**File: `src/netrc_auth.py`**

1. **Line 17 — Absolute NETRC paths get ~/ prefix** (Critical correctness bug)

   When the user sets `NETRC=/etc/netrc`, the code constructs `os.path.expanduser("~//etc/netrc")`, which resolves to `/home/user//etc/netrc` — not `/etc/netrc`. The standard NETRC convention (curl, git, wget) is that the variable holds the full path. This means the most common usage pattern simply does not work.

2. **Line 12 — Empty string `NETRC=""` treats home directory as netrc file** (Critical correctness bug)

   `os.environ.get("NETRC")` returns `""` for `NETRC=""`, which is not `None`, so `netrc_locations = ("",)`. Then `expanduser("~/")` is the home directory, `os.path.exists` returns True, and the code attempts to parse the home directory as a netrc file. Should skip empty strings.

3. **Line 17 — Relative NETRC paths expanded incorrectly** (Correctness bug)

   A value like `NETRC=../netrc` becomes `expanduser("~//../netrc")`, expanding to `/home/user/../netrc` instead of the intended `../netrc` relative to CWD. The `~/` prefix should not be added to paths that are already explicit.

4. **Line 11 — Inverts the established NETRC convention** (Correctness bug)

   The implementation treats NETRC as a filename relative to HOME (because of the `~/{name}` template), but the real-world convention is that it holds the full filesystem path. Users setting `NETRC=/path/to/netrc` following curl/git/wget conventions will silently fail.

**File: `tests/test_netrc_auth.py`**

5. **Line 34 — No test for absolute NETRC path** (Test coverage gap)

   The only test passes `".netrc-ci"` (a bare filename). There is no test with `NETRC=/absolute/path/to/netrc`, which is the most common usage pattern, so the absolute-path bug on line 17 goes undetected.

6. **Line 11 — Docstring omits NETRC env var documentation** (Documentation)

   The docstring does not mention the NETRC environment variable, so users cannot discover this feature without reading the source code.
