## Review: Use camera's own ffmpeg input args for audio

The change correctly refactors `get_ffmpeg_command` to resolve input args from the `FfmpegConfig` hierarchy instead of hardcoding `preset-rtsp-audio-only`. But the `or`-chain resolver is incomplete — it doesn't handle all three `FfmpegArgs` variants the config module documents.

### Correctness

**src/audio.py:16-19 — important — `TypeError` when `input_args` is a plain string of arguments.**

The config module (`src/config.py:3-4`) documents that `*_args` can be *"a preset name, a string of ordinary ffmpeg arguments, or a list of arguments"*. But the `or` chain doesn't handle the plain-string case:

```python
parse_preset_input(ffmpeg_input.input_args, 1)
or ffmpeg_input.input_args
or parse_preset_input(ffmpeg.input_args, 1)
or ffmpeg.input_args
```

When `ffmpeg_input.input_args = "-rtsp_transport tcp"` (a valid input per the config docs), `parse_preset_input()` returns `None` (line 19: `arg not in PRESETS_INPUT`), then `or ffmpeg_input.input_args` yields the raw string `"-rtsp_transport tcp"`. Concatenating `list[str] + str` on line 15 raises `TypeError`. Neither the input-level nor the camera-wide fallback is safe — both raw-string paths (`ffmpeg_input.input_args` on line 17 and `ffmpeg.input_args` on line 19) produce this error. No test exercises a plain-string `input_args`.

The fix is to pass the raw fallback through `get_ffmpeg_arg_list()`, which already handles both `str` and `list[str]` correctly (`src/ffmpeg_presets.py:25-27`).

**src/audio.py:16-19 — important — Empty list `input_args=[]` falls through to the camera-wide fallback.**

When `ffmpeg_input.input_args = []`, `parse_preset_input([], 1)` returns `None`, then `None or []` is falsy and falls through. An intentionally empty list is treated the same as unset. The `or` chain cannot distinguish "no result" (`None`) from "empty result" (`[]`). This is the same structural issue as the string case — the chain doesn't know when a value has been deliberately provided.

**src/audio.py:16 — nit — `detect_fps=1` injects `-r 1` for `preset-http-reolink`.**

`parse_preset_input(ffmpeg_input.input_args, 1)` hardcodes `detect_fps=1`. When the input preset is `preset-http-reolink`, `parse_preset_input` appends `"-r", "1"` to the args (line 21). The `-r` flag sets input frame rate — it has no meaning for an audio-only stream and is a leftover from the video detection use of this preset. Is `detect_fps` needed at all for audio, or should the call pass a value that suppresses the `-r` injection?
