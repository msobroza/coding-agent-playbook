## Review

### 1. Correctness

- **`src/feedstorage.py:27`** — `from_settings` reads `settings["FEED_STORAGE_FTP_ACTIVE"] or False` but never coerces the value to `bool`. `Settings` already provides `getbool()` for exactly this. When the setting is set via `-s FEED_STORAGE_FTP_ACTIVE=true` on the command line, `from_command_line` stores the raw string `"true"` (see `src/settings.py:27`). That string is truthy so `set_pasv(False)` happens, but `self.active` ends up being `"true"` instead of `True`. Should use `settings.getbool("FEED_STORAGE_FTP_ACTIVE", False)` instead.

- **`src/feedstorage.py:27`** — `or False` is redundant when `getbool()` is used (it already returns a `bool`). Even as-is, if the setting were explicitly set to `0` or `""` from the command line, `or False` happens to recover the right value — but it's a smell that the code is patching a missing conversion rather than doing the conversion.

### 2. Failure modes

- **`src/feedstorage.py:31-38`** — Pre-existing: `store()` opens an `FTP` connection without `with` or `try/finally`. If `ftp.cwd()` or `ftp.storbinary()` raises, `ftp.quit()` is never called and the connection leaks. Not introduced by this change, but the diff touches this method.

### 4. Design and boundaries

- **`src/settings.py:36-44`** / **`src/feedstorage.py:27`** — Information expert / coupling: `Settings` knows how to coerce command-line strings to bools via `getbool()`, but `from_settings` bypasses it. The setting accessor should be the single place that understands coercion.

### 5. Readability

- **`tests/test_feedstorage.py:17`** — The test passes `True` directly into the settings dict, so it exercises the boolean path but never the command-line string path. A test with `Settings.from_command_line(["FEED_STORAGE_FTP_ACTIVE=true"], {})` (or equivalent) would verify the coercion that `from_settings` actually needs.
