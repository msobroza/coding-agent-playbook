**Empirical verification** (ran the module under python3, exercising each NETRC value):

| NETRC value | Result | Expected |
|---|---|---|
| `/abs/path/.netrc-ci` (file exists) | `None` | credentials |
| `~/.netrc-ci` (file exists) | `None` | credentials |
| `""` (with valid `~/.netrc`) | `None` | credentials from `~/.netrc` |
| `/abs/path/.netrc-ci`, `HOME` unset | `None` | credentials |
| `.netrc-ci` (relative, the only case tested) | `('alice', 's3cret')` | credentials |

The root cause: the env var value — which the feature contract says is a **path** — is funneled into the same `f"~/{name}"` transform as bare home-directory filenames, so any absolute or tilde-prefixed value (the conventional `NETRC` usage per `netrc(4)`/curl) resolves to a nonexistent `~/…` path. A secondary defect: `is not None` lets an empty string through, yielding the home *directory* as the candidate, which passes `os.path.exists` and then fails in `netrc()` as `IsADirectoryError`.
