Findings from the 8 angles, deduped and ranked:

1. **Confirmed overcharge at exact-integer-kg boundaries (lb path).** `quote_cents(68.34330127731205, "lb")`: the true weight is 31 kg (68.34330127731205 = 31/0.45359237), but the float product is `31.000000000000004`, so `math.ceil` charges 32 kg (+120¢). Also `quote_cents(130.07273468907778, "lb")` → 59.00000000000001 → charged 60 kg. The multiplication by the inexact factor lands 1 ulp above the integer exactly when the parcel weighs a whole number of kg — precisely the case "every started kilogram is charged" should not extend to.
2. **NaN bypasses validation.** `float("nan") <= 0` is False, so `quote_cents(float("nan"), "lb")` passes the guard and dies inside `math.ceil` with `ValueError: cannot convert float NaN to integer` instead of the intended "weight must be positive" error (verified). Pre-existing in the touched function; the diff keeps this guard as the sole validation.
3. **Int > 2^53 behavior change on the kg path.** The removed line `math.ceil(weight)` was exact for ints; the replacement routes through `weight * 1.0` in `to_kilograms`, coercing to float: `quote_cents(2**53 + 1)` charged 9007199254740993 kg before, 9007199254740992 now (verified). Absurd magnitude, but a real, diff-introduced loss of exactness.
4. **Free-form unit string, case-sensitive, runtime-only.** `quote_cents(5, "LB")` or `"KG"` raises `ValueError`; the only discovery of valid units is via the error message. A `Literal["kg", "lb"]` (or case-normalized lookup) would catch typos/case at the definition site.
5. **Mutable shared pricing constant.** `KILOGRAMS_PER_UNIT` is a plain module-level dict imported into the pricing path; any imported caller can mutate it and silently change every quote. A frozen mapping (e.g. `MappingProxyType`/tuple) would make it read-only.
