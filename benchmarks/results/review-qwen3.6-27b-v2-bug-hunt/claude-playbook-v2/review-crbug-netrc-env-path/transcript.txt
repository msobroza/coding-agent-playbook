### Correctness

- **`src/netrc_auth.py:17`** — *important* — **Absolute `NETRC` paths are silently broken.** `f"~/{name}"` unconditionally prepends `~/` to the value. When `NETRC="/etc/secrets/netrc"`, this becomes `"~//etc/secrets/netrc"`, which `expanduser` resolves to `$HOME/etc/secrets/netrc` — a non-existent path in the user's home directory. The function returns `None` instead of reading the intended file. This is the most common real-world usage: CI systems and containerized environments set `NETRC` to an absolute path.

- **`src/netrc_auth.py:12`** — *important* — **Empty-string `NETRC` opens the home directory as a netrc file.** `netrc_file is not None` is `True` for `""`, so `netrc_locations = ("",)`. Line 17 then produces `f"~//"` → `"~/"`, which `expanduser` turns into the home directory. `os.path.exists()` returns `True` for a directory, so `netrc_path` becomes the home directory path. Line 29 then calls `netrc(home_dir)`, which raises `IsADirectoryError` (an `OSError`). With `raise_errors=True` this crashes; with the default it silently returns `None`. The guard should be `if netrc_file` (truthy), not `if netrc_file is not None`.

### Test Coverage

Add a test with an absolute path (e.g., `monkeypatch.setenv("NETRC", str(tmp_path / ".netrc-ci"))`) to verify the primary failure mode above.

### Security

- **`src/netrc_auth.py:17`** — *nit* — **Path traversal through `NETRC` resolves outside the home directory.** `NETRC="../.secret"` produces `os.path.expanduser("~/../.secret")`, which resolves to the parent of the home directory. The default `NETRC_FILES` (`".netrc"`, `"_netrc"`) can't do this, so it's new with the env-var support. Is this an intended or concerning behavior?
