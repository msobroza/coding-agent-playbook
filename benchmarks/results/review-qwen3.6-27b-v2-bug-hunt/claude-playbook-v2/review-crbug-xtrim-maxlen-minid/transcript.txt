

## Review

### Correctness

**`src/streams.py:34-48` — `important` — No guard requiring at least one of `maxlen` or `minid`.** Calling `xtrim("events")` with both `None` produces `pieces = []` (or `[b"~"]` if `approximate=True`), so the emitted command is `XTRIM events` or `XTRIM events ~` — neither includes a strategy keyword. Redis requires exactly one of `MAXLEN` or `MINID`; this command is rejected with a syntax error. The old signature required `maxlen` positionally, so callers that previously worked are now allowed to call it with no strategy at all.

**`src/streams.py:35-44` — `important` — No guard preventing both `maxlen` and `minid` from being set simultaneously.** Calling `xtrim("events", maxlen=100, minid="0-0")` produces `pieces = [b"MAXLEN", b"MINID", b"~", 100, "0-0"]`, which sends `XTRIM events MAXLEN MINID ~ 100 0-0`. The Redis 6.2 grammar is `XTRIM key <MAXLEN | MINID> [= | ~] threshold [LIMIT count]` — the angle brackets with `|` mean exactly one strategy. This command is rejected.

**`src/streams.py:39-40` — `important` — `b"~"` is placed after both strategy keywords when both are provided.** When `maxlen` and `minid` are both set with `approximate=True`, the tilde lands between `MAXLEN` and `MINID`: `MAXLEN ~ MINID 100 0-0`. The `~` must immediately follow the single chosen strategy keyword, not float between two. This is a structural consequence of the keyword-ordering bug above, but the placement logic is independently wrong — the `approximate` check fires unconditionally without knowing which (if any) strategy it belongs to.

**`src/streams.py:45-47` — `important` — `LIMIT` appended even when no strategy exists.** Calling `xtrim("events", limit=10)` with both strategies `None` produces `XTRIM events ~ LIMIT 10`. The `LIMIT` clause is only valid as part of a `MAXLEN` or `MINID` subclause; without a strategy, Redis rejects this.

**`src/streams.py:43-44` — `important` — `minid` threshold appended as a bare `str` while all keyword tokens are `bytes`.** `pieces.append(minid)` pushes a Python string (`"1700000000000-0"`) alongside `b"MINID"`, `b"~"`, and `b"LIMIT"`. The `maxlen` value is an `int`, which Redis clients auto-coerce, but a bare string mixed with bytes tokens is an encoding inconsistency that depends on the executor to handle correctly. It should be encoded to bytes (e.g., `minid.encode()`) for consistency.

**`tests/test_streams.py:31-32` — `important` — No test for the `minid` + `limit` combination.** The test suite covers `maxlen`-only, `minid`-only, and `maxlen`+`limit`, but not `minid`+`limit`. This is the one valid two-strategy-less-one combinatorial case that remains untested.

**`tests/test_streams.py` — `important` — No test for any of the invalid input combinations** (neither strategy, both strategies, `limit` without strategy). A test that asserts these raise would both guard against the bugs above and document the intended API contract.

### Design and Boundaries

**`src/streams.py:22-25` — `nit` — The signature uses two independent optional parameters (`maxlen: int | None`, `minid: str | None`) for what Redis defines as a mutually exclusive choice.** This puts the mutual-exclusivity burden on the caller and the implementation. A keyword-only union or enum parameter (e.g., `strategy: TrimStrategy`) would make the contract machine-checkable. Simplicity principle: the API surface should reflect the invariant, not hide it in runtime checks.

### Readability

**`src/streams.py:27-32` — `nit` — The docstring does not state that exactly one of `maxlen` or `minid` is required**, nor does it mention the mutual exclusivity constraint. Callers reading only the docstring would not know that passing both is invalid.

### pre-existing

**`src/streams.py:39-40` — `pre-existing` — When `approximate=False`, neither `b"~"` nor `b"="` is appended.** The Redis grammar offers `[= | ~]`, where `=` means exact trimming. The old code already omitted the operator entirely when `approximate=False`, relying on the server default. This predates the diff but is worth noting.
