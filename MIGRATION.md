# Migration guide

> **Heads-up:** **v0.21** moves every scoped rule into a skill. A repo or overlay with its own
> scoped rules must add `skill: <skill-id>` to each one, or `playbook sync` refuses them. A
> repo-local rule that joins a core skill also needs `section:` and a priority inside that
> section's impact band. Run `playbook validate` before upgrading. Member rules are now
> written to `<skill>/rules/<rule-id>.md`, and four scoped rule ids in core are retired;
> see the v0.21 TL;DR.
>
> **v0.20** (assistant lifecycle hooks, below) asks one thing of every
> consumer: run `playbook validate` before upgrading, because `playbook sync` now
> refuses content that validate rejects. Everything else in v0.20 is opt-in or a
> one-time diff; its TL;DR says who must act.
>
> Older: the **v0.13 task-config redesign** supersedes parts of the
> v0.12 guide. The authored `[expected]`/`[metrics]`/`[rubric]` task TOML that v0.12
> called "unchanged" is **gone** — replaced by the `[gate]`/`[rubric]`/`[verdict]`/
> `[aggregate]` layers — and `higher_is_worse` is replaced by a per-`Metric`
> `Normalizer`. Read the v0.13 section before the v0.12 one; the v0.12 section still
> applies to the engine `Metric`/`Check`/`Rubric` API and the entry-point group renames.

## Module paths

The engine modules are moving into packages named after the glossary concepts
(design `specs/prT-package-layout.md`). A move leaves no re-export at the old
path, so out-of-tree code that imports an engine module (an adapter, a metric, a
hook handler) must import it from its new path. Configuration, rule ids, hook ids,
the console scripts (`playbook`, `coding-agent-playbook`, `playbook-hook`),
`python -m coding_agent_playbook.cli`, `coding_agent_playbook.adapters.base` and the
entry-point groups do not change. The table lists every moved module path that
out-of-tree code can import (public old or new path):

### `package_manager` and per-key validation

- **New key.** `applies_if: {package_manager: uv}` gates a rule, prompt or hook on the
  detector's existing `package_manager` fact; a list such as `[uv, poetry]` means any
  of them. The names are `uv`, `poetry`, `pip-tools` and `pip`. A repo with no detected
  package manager never matches, and an unknown name fails `playbook validate` in every
  repo, naming the value and the four allowed names (SPEC §6.4).
- **Behaviour change.** `playbook validate` used to pass a rule's or prompt's whole
  `applies_if` to the evaluator, which stops at the first key that does not hold, so a
  malformed key after it went unseen: `{has_framework: [django], orm_version: ">=2"}`
  passed in every repo without Django. Each key is now checked on its own, as hooks
  and `lint_codes.when` already were, so an overlay or repo-local artifact with such a
  hidden typo now fails `playbook validate`, and therefore the validate-gated
  `playbook sync`. Fix the key it names; nothing else changes.

### The shared_skills adapter writes .agents/skills/

The shared-skills adapter (`shared_skills`, id unchanged) used to write its
copies to `shared_skills/<id>/`, a directory no harness reads. It now writes the
shared skill root `.agents/skills/<id>/`, which Codex reads natively (in every
directory from the project root to the working directory) and OpenCode scans as
a compatibility root. The bytes are unchanged: each copy is still identical to
`.claude/skills/<id>/` and `.opencode/skills/<id>/`.

The engine declares `shared_skills/` as a *retired output location*, so the
first write-mode `playbook sync` after the upgrade (run by hand, or by the
post-checkout / post-merge hook) settles it like any leftover:

1. It writes `.agents/skills/<id>/` and records those lockfile rows with
   `adapter = "shared_skills"`.
2. It deletes every `shared_skills/` file the previous lockfile lists whose
   bytes still match and that git does not track, then prunes the emptied
   directories, `shared_skills/` included.
3. It swaps `/shared_skills/<id>/` for `/.agents/skills/<id>/` in the managed
   `.gitignore` block; with hooks on, `guard_config.json` follows.

What is kept, never silently left behind:

- A file you edited, or one git tracks, stays on disk and stays owned: it is
  still in the lockfile and, under `commit = false`, in the managed block (as
  `/shared_skills/<id>/` while its `SKILL.md` is kept, else one entry per file).
  Under `commit = true` the sync lists it on stderr (`note: kept output …`);
  delete it with `git rm -r shared_skills` once you have committed
  `.agents/skills/`. Until then the legacy `playbook-sync-check` hook reports
  drift.
- A file you wrote yourself inside `shared_skills/` was never in the lockfile,
  so it is never deleted.
- While an enabled adapter is missing (including a listed `codex`, below),
  every leftover is kept and the cleanup waits until the list is fixed.

Before that first sync, `playbook sync --check` exits 1 and lists the move:

```text
Drift detected:
  .agents/skills/<id>/SKILL.md
    Missing on disk; run 'playbook sync' to create.
  shared_skills/<id>/SKILL.md
    Orphaned generated file; run 'playbook sync' to remove.
  .gitignore
    Managed block is missing or stale ([output] commit = false).
    Run 'playbook sync' to regenerate.
```

Scripts, CI globs and mypy or ruff excludes that point at `shared_skills/` must
point at `.agents/skills/`. `mypy .` skips dot-directories, so the default
adapters no longer expose any skill script copy to it: the duplicate-module
error that `shared_skills/` plus `agent_harness`'s `skills/` used to cause is
gone. `ruff check .` behaves as before.

OpenCode now finds each skill in up to three roots (`.opencode/skills/`,
`.agents/skills/`, `.claude/skills/`). v2 keeps one copy by precedence
(`.opencode` over `.agents` over `.claude`). v1 logs one duplicate-skill warning
per extra copy; set `OPENCODE_DISABLE_EXTERNAL_SKILLS` (drops `.agents` and
`.claude`) or `OPENCODE_DISABLE_CLAUDE_CODE_SKILLS` (drops `.claude`) to silence
it. The engine sets neither.

### playbook init no longer enables Continue

`playbook init` without `--adapters` now writes
`adapters_enabled = ["claude_code", "opencode", "shared_skills"]`. Continue is
opt-in: its upstream is in a maintenance freeze, and its IDE already loads the
root `AGENTS.md` and `.claude/skills/` without an adapter of its own. To opt in:

```bash
playbook init --adapters claude_code,opencode,shared_skills,continue
```

A repo whose committed `adapters_enabled` already lists `continue` keeps it on
every `init` re-run and every sync, and its `.continue/` output is exactly what
it was. To drop Continue, remove `"continue"` from `adapters_enabled`: the next
sync deletes its unchanged `.continue/rules/` and `.continue/prompts/` files as
leftovers.

### "codex" in adapters_enabled

Older versions of the interactive `playbook init` offered a `codex` choice, but
no adapter provides it. A listed `codex` made every sync warn that an adapter is
missing and keep every leftover, which also blocks the `shared_skills/`
cleanup above. The interactive choices no longer offer it, and the warning now
names the fix:

```text
'codex' is not an adapter: Codex reads AGENTS.md and .agents/skills/ (the shared_skills adapter); remove it from adapters_enabled.
```

Remove `"codex"` from `adapters_enabled`. Codex is served by `AGENTS.md` and
`.agents/skills/`.

### Not changed (shared_skills and Continue)

- Continue output when `continue` is enabled: `.continue/rules/` and
  `.continue/prompts/` are byte-identical to the previous release.
- `.claude/skills/` and `.opencode/skills/`, and the skill bytes in every root.
- The lockfile schema (still 2) and the adapter id `shared_skills`, so a
  committed `adapters_enabled` needs no edit.

### AGENTS.md and the Claude Code rules file hold only always rules

A member rule, a scoped rule that names a skill in `skill:`, is no longer
written into `AGENTS.md` or `.claude/rules/coding-agent-playbook.md`
(`CLAUDE_RULES_PATH`). It reaches Claude Code, OpenCode and Codex as a
rule file of its skill, `<skills root>/<skill>/rules/<rule-id>.md` (see
"Member rules move to rules/"), and Continue still gets it as its own rule
file. Both files now carry the always rules, then one generated
`## Where guidance lives` section, byte-identical in the two, with one line
per written skill that has member rules and a `playbook.files` phrase:

    - Risk model modules: skill `risk-models`

`AGENTS.md` then ends with its Guardrails section; the rules file ends with the
heartbeat line when the session-start briefing is on. An always rule keeps its
full section. `.claude/CLAUDE.md` stays the four-line stub. Every
scoped rule in core names a skill, so every repo sees the change: in a typical
FastAPI + ML repo with hooks on, `AGENTS.md` shrinks from about 6,800 words to
about 1,850, of which about 330 come before the Guardrails section, and the
Claude Code rules file from about 5,300 words to about 350 (with the shorter
always text below). A later change of this release shortens the guardrails to
one line per hook, so with every v0.21 change `AGENTS.md` ends at about 800
words, about 470 of them in the Guardrails section (see "Guardrails and lint
feedback point at skills").

The map names only skills that a sync writes. When no enabled adapter writes a
skills root (`adapters_enabled = []`, or only `continue`), `AGENTS.md` has no
`## Where guidance lives` section.

When member rules are active but every enabled adapter is `agents_md`
(`adapters_enabled = []`), nothing delivers them, and `playbook sync` says so on
stderr instead of inlining them into `AGENTS.md`:

    warning: no enabled adapter delivers scoped rules (only agents_md is on); skill risk-models reaches no assistant: add claude_code, opencode or shared_skills to adapters_enabled

### Scoped rules arrive as skill references

Every scoped rule in core belongs to one core skill (`python-coding`,
`python-testing`, `python-tooling`, `ml-data` or one of the "New core skills"),
and is now `<skills root>/<skill>/rules/<rule-id>.md`, listed in that skill's
index, for example `.claude/skills/python-coding/rules/python-typing.md`. A skill
is written only when at least one of its rules applies to the repo, so a repo
without pytest has no `python-testing`. The ids that hooks, `lint_codes` and
prompt `includes_rules` name are kept (four other ids are retired, see "Vendored
upstream Python guidance"); lint feedback now names the rule id and its skill
(see "Guardrails and lint feedback point at skills"), so open that skill's rule
with that id. The `python-coding` members have short display
names (`Typing`, `Error handling`, …) because each name is its label in the
skill's description, and `python-typing`, `python-error-handling`, `pytest` and
`fastapi-app-wiring` have new one-line descriptions, because a description is
now the rule's line in its skill's index. Prompts that inline these rules show
the new names in their `## Reference rules` headings (`### Error handling`).

### The always text is shorter

`project-context` keeps the name, kind and description and two reminders: ask
before coding when the scope or approach is unclear, and report problems outside
the task instead of fixing them in the same change. The kind now reads
`(project kind: …)` and is still the detector's. The reminders "read existing
code first", "prefer clarity over cleverness" and "keep changes minimal" are
gone. `python-house-style` keeps seven bullets (its layout line moved to the
new `code-legibility` rule, see "New always rules and the layout guard"), some
with a one-line reason; the rest moved to two new rules in `python-coding`:
`python-data-shapes` (records, frozen dataclasses, return shapes, constants) and
`python-idioms` (paths, flag-driven functions, composition, strings, imports,
small idioms). Neither always rule has a title heading of its own any more (the
`## Project context` and `## Python house style` headings stay), and both are at
`version: 3`. In a typical FastAPI + ML repo the two sections shrink from about
690 words to about 230. An override of either always rule by id keeps its own
text, and with it its old length.

### Add skill: to your own scoped rules

```yaml
# playbook/rules/risk-models-specific.md.j2: before
scope: scoped
globs: ["src/risk/**/*.py"]

# after
scope: scoped
skill: python-coding
section: effects
priority: 58
globs: ["src/risk/**/*.py"]
```

`python-coding` declares sections, so a repo-local rule that joins it also names
one of them in `section:` and takes a priority inside that section's impact band
(see "Sections and impact bands"). Without `skill:`, `playbook validate` and
`playbook sync` stop with:

    scope 'scoped' needs a skill: put the file in that skill's rules/ directory (skills/<skill-id>/rules/), or add 'skill: <skill-id>' when the skill comes from another layer; known skills: design-patterns, domino-agents, domino-apps, domino-jobs, ml-data, playbook-creator, python-architecture, python-coding, python-documentation, python-testing, python-tooling, web-application

The list names every skill that can take rules after your layers are merged, so
a skill of your own joins it. When the rule overrides a rule in core by id, the
line ends with the skill the overridden rule named, for example
`; the rule it overrides (coding_agent_playbook) names 'python-coding'`.

Pick the skill by topic: `python-coding` for line- and function-level Python,
Pydantic included, `python-testing` for tests, `python-tooling` for one named
developer tool (linter, type checker, formatter, test settings, package
manager), `ml-data` for ML and data libraries, `web-application` for web
endpoints and their database, `design-patterns` for the shape of code inside a
module, `python-architecture` for how modules depend on each other (see "New
core skills"). To keep a rule in a skill of your own, add
`playbook/skills/<id>/SKILL.md` with a capability sentence in `description` and
a `playbook:` block (`use_when`, `files`); a skill without that block, such as a
bundled plugin skill, cannot take rules. Always rules must not carry `skill:`.

### Continue and the new rules

Continue still gets one rule file per rule, `NN-<rule-id>.md` with `NN` its
priority, and ignores `skill:` and `section:`. `.continue/rules/` gains
`python-data-shapes` and `python-idioms`; `00-project-context.md` and
`10-python-house-style.md` get the shorter text. The `python-coding` members
show their new short names, and four show their new descriptions. Every scoped
rule's priority now follows its section's impact band, so every
`.continue/rules/` file of a scoped rule changes its name (see "Continue file
names follow the impact bands").
Core skills are not turned into Continue prompts, so no
`.continue/prompts/<core-skill>.md` is ever written.

### New output and the lockfile

Each written core skill adds `<root>/<id>/SKILL.md` and `rules/` (plus
`references/` for its free-form documents and license copies) under every
enabled skills root, one lockfile entry per file (`kind = "skill"` for
`SKILL.md`, `kind = "rule"` with the rule id for each rule file, so the
generated-output guard points an editor at the rule) and, with
`[output] commit = false`, one managed `.gitignore` line per skill directory.
Nothing is removed. A hand-written skill directory of yours named
`python-coding` (or another core id) is left alone with a warning; rename it, or
move it to `playbook/skills/python-coding/` to override the core skill (keep its
`playbook:` block: the core rules still attach to it).

### Not changed (skill references)

The rule ids that hooks and prompts name, `lint_codes`, `linked_rule` hooks,
prompt rendering (until "Prompts point at skills" below), the lockfile
schema and Claude Code's `.claude/CLAUDE.md` stub.

### Guardrails and lint feedback point at skills

Lint feedback names the skill that holds the fix. After the next
`playbook sync`, a lint hook linked to a rule that names a skill prints

    rule python-error-handling (skill python-coding): "src/app.py:4 E722 Do not use bare `except`"

instead of `rule python-error-handling: …`, and a finding CI also fails on ends
in `(rule python-error-handling, skill python-coding)` instead of
`(rule python-error-handling)`. The skill travels in `guard_config.json`, as
`"skill"` next to `"rule"` and `"warn"` in the hook's `lint_codes`. A rule
without a skill (an always rule that carries `lint_codes`) keeps the old
`rule <id>:` prefix, and so does a `guard_config.json` written before this
change until sync rewrites it: nothing fails in between. Tooling that matches
the old prefix exactly should accept the `(skill …)` part. Decision-log rule
ids and the resync hook's "rule <id>" message are unchanged. On OpenCode v2 the
generated plugin is an inert `setup()` stub (SPEC §10.6.2), so no lint feedback
runs there at all until the shim is ported.

A new feedback hook, `skill-nudge` (tier `default`, on whenever hooks are on),
names the skill that covers a file the first time a session edits it:

    Conventions for this file: skill python-coding.

It prints one line per skill whose member rules' globs match the edited file,
each line at most once per session, and stays silent when the hook state
directory is unusable (it could not keep the once-per-session promise). In a
FastAPI + ML repo the first Python edit names `ml-data`, `python-coding` and
`python-tooling`, and the first test edit after it names `python-testing`
alone. Sync derives the glob table from the member rules it writes, as
`"skills"` in the hook's `guard_config.json` record; no layer can set it. The
`✓ Hooks:` summary counts one more hook (`30 enabled` where 29 were on, and
`claude_code: 30 enforced`), `playbook check` lists it as enforced on Claude
Code and degraded on OpenCode (it also matches notebook edits, and OpenCode has
no notebook tool; see "Distilled python-best-practices content"), and
`.claude/settings.json` gains no managed entry: edits and writes already reach
the hook launcher, and the existing `PostToolUse` entry's matcher only gains
`NotebookEdit`. The hook has no body, so `AGENTS.md`
and Continue get no text for it. To turn it off, add
`disable = ["skill-nudge"]` to `[hooks]`. OpenCode v2 runs neither the nudge
nor the `rule <id> (skill <skill>)` lint feedback: its plugin is the inert stub
above, so there only always-loaded context and the skill listing point at
skills until the shim is ported (SPEC OQ-11).

Core ships a fifth skill, `playbook-guardrails`, that holds the full text of
every guardrail the repository enables. It takes no member rules: with hooks
on, sync composes it from the on hooks, one section per hook with guardrail
text, sorted by hook id, each the hook's body and its "Enforced by lifecycle
hooks on: …" line under a ``## <name> (`<id>`)`` heading. The next
`playbook sync` writes `.opencode/skills/playbook-guardrails/SKILL.md` and
`.agents/skills/playbook-guardrails/SKILL.md` (byte-identical), with one
lockfile entry each (`kind = "skill"`, artifact id `playbook-guardrails`) and,
with `[output] commit = false`, one managed `.gitignore` line each. Claude Code
runs the core hooks itself, so `.claude/skills/` gets the skill only for a hook
it cannot run (an overlay hook without `claude_code` in `supports`); Continue
and `agent_harness` keep their guardrail text as before (`AGENTS.md` keeps one
line per hook, below), and Continue gets no prompt for the skill. With
`[hooks] enabled = false`, or `advisory = false`, no copy is written, and the
copies an earlier sync wrote are
settled by the leftover policy like any removed skill. A skill of yours with the
id `playbook-guardrails` in `playbook/skills/` or an overlay replaces the
authored description and intro; the hook sections are still added.

`AGENTS.md`'s `## Guardrails` section shrinks to one line per hook with
guardrail text, sorted by hook id, under a new preface that names the skill:

    ## Guardrails

    Lifecycle hooks enforce these on assistants that run them; on every other assistant, follow them yourself. Skill `playbook-guardrails` has the full text of each one and where it is enforced.

    - `block-precommit-bypass`: This repository's pre-commit hooks must run on every commit.
    - `stop-ci-parity-gate`: Before claiming done, run `ruff check .`, `ruff format --check .`, the type checker and the tests; report the results.

The `### <name>` block and the italic "Enforced by lifecycle hooks on: …" line
of each hook move to the skill. In a FastAPI + ML repo with the default hooks
the section drops from about 1,500 words to about 470, and the whole file to
about 800. Each line is the hook's new optional `summary` in `HOOK.md`: one line
of 1-120 characters without `{{` or `{%` (frontmatter is never rendered), which
every core hook with a body now declares. An overlay or repo-local hook needs no
edit: without `summary` its line is the first sentence of its rendered body
(headings skipped, list and quote markers dropped), cut at a word boundary with
`…` once it passes 120 characters. A malformed one is a
`FAIL` line of `playbook validate`, and so stops `playbook sync`:

    FAIL playbook/hooks/x/HOOK.md: summary: expected a single line of 1-120 characters without '{{' or '{%', got '…'

A hook Claude Code cannot run (an overlay hook without `claude_code` in
`supports`) gets one line in a `## Guardrails` section of
`.claude/rules/coding-agent-playbook.md`, after the Where section, instead of a
full `## Guardrail: <name>` section; its full text is in
`.claude/skills/playbook-guardrails/`. With the core hooks every hook runs
natively, so the rules file has no Guardrails section. With `[hooks] enabled =
false` or `advisory = false` there is no Guardrails section anywhere. Continue's
`.continue/rules/30-guardrail-<id>.md` and `agent_harness`'s
`rules/30-guardrail-<id>.md` are byte-identical; the `.playbook/hooks/<id>/HOOK.md`
sidecar and its `.playbook/manifest.toml` entry copy the canonical frontmatter,
so they gain `summary`. With
`opencode` and `shared_skills` both off, the preface names a skill no
`AGENTS.md` reader can load, like the Where lines; enable one of them. On
OpenCode v2, whose plugin is the inert stub above, these lines and the Where
section are what point at skills.

### Vendored upstream Python guidance

Core now vendors two outside sources instead of writing their ideas fresh: the
python-best-practices agent skills (Ludo Technologies LLC, MIT) and the
python-clean-architecture Claude Code plugin (MKToronto, MIT), each at one pinned
commit (decision record
`docs/adr/0004-upstream-python-guidance-is-vendored-into-core.md`). The upstream
text is the base of each rule, adapted to the engine's frontmatter and this
repo's toolchain, with no URLs; `catalog/core/ATTRIBUTIONS.md` maps every
upstream file to the core rules and references it became, or says why it was
dropped. There is nothing to do but `playbook sync`; what changes:

- **License copies.** Each core skill that holds vendored text ships the MIT
  notice it carries, byte for byte, as `references/LICENSE.python-best-practices`
  and/or `references/LICENSE.python-clean-architecture`. The next sync writes
  them under every enabled skills root next to the skill's rules, with one
  lockfile entry each, like any other skill file; leave them in place when you
  commit the output. Continue gets no license copy, since it receives rule files
  only.
- **One topic per rule.** The old multi-topic rules are split to one topic per
  file of at most 100 lines. A split keeps the old id on the piece with the old
  topic, so every id a hook (`linked_rule`), a prompt (`includes_rules`) or
  `lint_codes` names still exists: `python-typing`, `python-error-handling`,
  `python-docstrings`, `python-dependency-injection`, `python-pure-core`,
  `pytest` and `ml-serialization-security`. Their bodies change, and so does the
  text of the prompts that include them; eval scores taken before this release
  are not directly comparable.
- **Four ids are retired.** Each one's topics now live in the rules below, and
  the retired id is never reused:

  | Retired id | Its skill | Successor rules |
  |---|---|---|
  | `python-performance-idioms` | `python-coding` | `python-collection-choice`, `python-comprehensions`, `python-generators`, `python-optional-keys`, `python-str-join` |
  | `python-classes-and-protocols` | `python-coding` | `python-protocols`, `python-properties` (`python-coding`); `design-single-responsibility`, `design-lightest-construct`, `design-composition-over-inheritance`, `design-liskov-substitution`, `design-interface-segregation`, `design-open-closed`, `design-dry-yagni-kiss` (`design-patterns`) |
  | `ml-dtypes-and-typing` | `ml-data` | `ml-dtypes-at-load`, `ml-check-after-load`, `ml-frame-validation`, `ml-numpy-dtypes`, `ml-categorical-labels`, `ml-array-typing` |
  | `ml-reproducibility-and-testing` | `ml-data` | `ml-seeded-randomness`, `ml-numeric-assertions` |

  The next sync stops writing the retired rule files and settles the copies an
  earlier sync wrote as leftovers. An overlay or repo-local rule with a retired
  id no longer overrides anything: it becomes a rule of its own, which then
  needs `skill:` (and, for a core skill, `section:`; see "Sections and impact
  bands"). Give it one of the successor ids to keep overriding, or a new id.
- **Sections.** Each of the four skills groups its rules into sections by
  impact, and its index lists them CRITICAL first: `python-coding` has Error
  handling, Code shape, Names, types, docs, Effects and resources, Asyncio,
  Pydantic validation, Classes and data shapes, Control flow, and Idioms and
  performance; `python-testing` has Mocking, Test Structure, Test Isolation,
  Fixtures, Parametrization and Coverage; `python-tooling` has Linting, Type
  checking, Formatting, Test configuration and Package management; `ml-data`
  has Serialization Security, Vectorization, Indexing & Mutation, Dtypes &
  validation, Reproducibility, Chaining style, Typing and Testing. Each skill's
  description names its sections in its "Covers" clause.
- **Rules change skill.** `pydantic-boundaries` moves from `python-tooling` to
  `python-coding` (Pydantic validation), still gated on `pydantic` being a
  declared dependency, so a FastAPI repo that gets Pydantic only through FastAPI
  does not get it; `pydantic-typed-settings` needs `pydantic-settings`.
  `fastapi-app-wiring` and `fastapi-error-boundaries` move from `python-tooling`
  to the new `web-application` skill, still gated on FastAPI. Their files move
  to the new skill's `rules/` directory in the output.
- **`python-tooling` names tools only.** It holds the linter, type checker,
  formatter, test-settings and uv rules, and is written in every Python repo,
  because `python-static-checks` is ungated. Its line in "Where guidance lives"
  reads `Tool configuration and pyproject.toml` (it read `Tool configuration and
  framework wiring` in earlier v0.21 builds, and named FastAPI before them). Its
  rules also match `pyproject.toml` and the ruff, mypy and pytest config files,
  so with hooks on an edit of one of those files makes `skill-nudge` name
  `python-tooling` (still at most once per session). Creating a `uv.lock` by
  hand or with `uv lock` alone does not trigger the resync hook, so the uv rules
  appear at the next `playbook sync`.
- **Version branches instead of version gates.** `python-typing`,
  `python-async` and the new asyncio rules no longer require Python 3.11: a repo
  on 3.10 now gets them, and their examples render the form the repo's detected
  Python version accepts (for example `TaskGroup` and `asyncio.timeout` from
  3.11, `gather` and `wait_for` below it). Only the few rules whose topic does
  not exist before 3.10, such as the `match` rules, keep a
  `python_version: ">=3.10"` gate.
- **Library gates in `ml-data`.** A repo whose ML stack includes NumPy, pandas
  or polars gets the vectorization, mutation, dtype, reproducibility, chaining,
  typing and testing rules for the libraries it declares; each renders only the
  sections for those libraries, and they also match `**/*.ipynb`. A repo with
  torch alone gets `ml-serialization-security` only. `ml-frame-validation` also
  needs `pandera`. `ml-data`'s line of "Where guidance lives" reads "Model, array
  and data-frame code: skill `ml-data`".
- **`skill-nudge` covers notebooks.** It also matches `notebook_edit`, so a
  Claude Code notebook edit nudges `ml-data`: the next sync rewrites the
  managed `PostToolUse` entry of `.claude/settings.json`, whose matcher gains
  `NotebookEdit`. `playbook check` now labels the hook `degraded` on OpenCode,
  which has no notebook tool; OpenCode writes of `.py` and `.ipynb` files still
  nudge, and `playbook validate` reports no warning for it.
- **New gates.** Rules can gate on declared packages with two new `applies_if`
  keys, which read runtime and dev dependencies alike (names PEP 503-normalized):
  `has_dependency: [pydantic-settings]` holds when every listed package is
  declared, `any_dependency: [sqlalchemy, alembic]` when at least one is. They
  are open to overlay and repo-local rules, prompts and hooks too. They read
  `[project].dependencies`, the dev groups of `optional-dependencies` and
  `[dependency-groups]` in `pyproject.toml`, and the names in root
  `requirements*.txt` files. A package declared only in Poetry tables, a
  nested requirements file or `setup.py` leaves them off.
- **Overrides.** An overlay or repo-local rule whose id is one of the new ids
  now replaces the core rule, like any rule with the same id; `playbook check`
  shows which one won. A repo-local override of a kept id such as `pytest` keeps
  its own text, so the guidance split out of it then lives only in the new
  rules.
- **Not changed.** The ids above that hooks, prompts and `lint_codes` name, and
  every rule's `lint_codes`, so lint feedback reports exactly what it did
  before. `playbook sync --check` reports drift until the repo re-syncs, as for
  any content upgrade.

### Prompts point at skills

`includes_rules` is now the only way a prompt declares the rules it needs, and
each harness gets them its own way. Claude Code and OpenCode commands carry no
rule text: a command whose `includes_rules` lists an active scoped rule opens
with a generated `## Before you start` block, before its first `##` section,
naming the skill and the rule file to read, for example in
`.claude/commands/review.md`:

```markdown
## Before you start

1. Load skill `python-coding` and read its rules `rules/python-typing.md`, `rules/python-error-handling.md`.
2. For each file in scope, also load any other listed skill whose description matches it.
```

| Consumer | Before | After |
|---|---|---|
| Claude Code `.claude/commands/<slash>.md` | rule bodies: in place for `review`, `generate-tests` and `security-review`, else a `## Reference rules` appendix | the `## Before you start` block; no rule body |
| OpenCode `.opencode/command/<slash>.md` | as Claude Code | the same block, after the `description:` envelope |
| Continue `.continue/prompts/<slash>.md` | as Claude Code | a `## Reference rules` appendix at the end, each included rule once |
| agent_harness `prompts/<slash>/SKILL.md` | the Claude Code command text | the appendix at the end (byte-identical for a prompt that never called `rule()`) |
| `playbook eval` | the body with the three prompts' `rule()` expansions, never an appendix | the body plus the appendix, the text Continue gets |

An always rule, a rule whose `applies_if` is false and an unknown id get no
line, and a prompt with no active reference gets no block at all: `/explain`
and `/find-injected-vulnerability` render byte-identically. For `review` on
Continue the rules now follow `## Output format` instead of preceding it.

The `{{ rule() }}` Jinja helper is gone from every template. A repo-local or
overlay prompt that still calls it fails `playbook validate`, and so
`playbook sync` writes nothing, with the message below; the pre-commit
`playbook sync --check-staged` (not otherwise validate-gated) refuses the
commit with it too:

    <path>: body calls {{ rule("python-typing") }}; prompts no longer inline rules. Remove the call and keep 'python-typing' in includes_rules: Claude Code and OpenCode commands then point at its skill, Continue appends its text

Before:

```markdown
---
id: tidy
name: Tidy
description: Tidy a module
slash: tidy
includes_rules:
  - python-typing
---
Tidy the module without changing behaviour.

## Reference rules

{{ rule("python-typing") }}
```

After (the file may now be plain `.md` when nothing else in it needs Jinja):

```markdown
---
id: tidy
name: Tidy
description: Tidy a module
slash: tidy
includes_rules:
  - python-typing
---
Tidy the module without changing behaviour.
```

Two more validate errors guard the list, since a typo there would now drop
guidance silently: `includes_rules` must be a list of rule ids (a bare
`includes_rules: python-typing` used to be read letter by letter), and every id
must name a rule in core, an enabled overlay or `playbook/rules/`, with a
did-you-mean. A rule that `applies_if` filters out in your repo is still a
valid id. `playbook render <prompt> --show-rules` now names each rule's
delivery (`-> skill python-coding, rules/python-typing.md`, `-> always
loaded`, `OMITTED`, `UNKNOWN`).

No file is added or removed, so there are no orphans. The next sync rewrites
every `.claude/commands/*.md` and `.opencode/command/*.md` of a prompt with
`includes_rules`, the three Continue prompts and agent_harness leaves of
`review`, `generate-tests` and `security-review`, and their lockfile hashes;
`playbook sync --check` reports drift until then. Eval scores taken before this
release are not directly comparable: the runner now appends the rules to every
task whose prompt lists them. On OpenCode, `/review` and `/security-review` run
as the read-only `plan` agent; that this agent may load a skill is not yet
verified on OpenCode v1.19.3 and v2.0.32 (SPEC §10.6.1).

Python API, for overlay code that calls the renderer: `build_environment` takes
only the template search paths (`is_prompt_context` and `rule_registry` are
gone), `render_for` takes `skill_references` and no longer `template_body`, and
`renderer.appendix_rule_ids` and `harness.emitter.strip_leading_sentinel` are
removed.

### Member rules move to rules/

Member rules now live in their skill's `rules/` directory, in the catalog and in
the output (decision record
`docs/adr/0005-member-rules-live-in-their-skills-rules-directory.md`). The next
sync writes each one as `<skills root>/<skill>/rules/<rule-id>.md` under
`.claude/skills/`, `.opencode/skills/` and `.agents/skills/`, with a
`kind = "rule"` lockfile entry, and `references/` keeps only free-form
documents and license copies. Earlier v0.21 builds wrote the same file as
`<skills root>/<skill>/references/<rule-id>.md`. The first write-mode sync after
the upgrade settles those copies through the lockfile leftover policy:

- An old copy whose bytes still match and that git does not track is deleted,
  with its lockfile row.
- A copy you edited, or one git tracks, stays on disk and stays owned (still in
  the lockfile). Under `commit = true` the sync lists it on stderr
  (`note: kept output …`). Move what you added into a repo-local override of the
  rule (same id), then delete the old copy.

`agent_harness` follows: it used to write every scoped rule at the root of its
tree as `references/<rule-id>.md`, routed by `references/REFERENCES.md`; it now
writes each member of an emitted skill at `skills/<skill>/rules/<rule-id>.md`,
and the next sync settles the old root copies the same way. `playbook
import-harness` reads the new layout back.

Generated text says "rules" for these files: each skill's index is a
`## Rules` section, `playbook render <prompt> --show-rules` prints
`-> skill python-coding, rules/python-typing.md`, and a prompt's
`## Before you start` step reads:

```markdown
1. Load skill `python-coding` and read its rule `rules/python-typing.md`.
```

A `SKILL.md` of yours must not author a `## Rules` heading, because the engine
generates it.

In your own layers, a skill may now carry its rules the same way:
`playbook/skills/<skill-id>/rules/<rule-id>.md` (or an overlay's
`skills/<skill-id>/rules/`) belongs to that skill without `skill:`, must not
name another skill in `skill:`, and must be named after its id;
`playbook validate` fails otherwise, and also on two rules with one id in one
layer. A scoped rule in `playbook/rules/` or an overlay's `rules/` keeps its
free file name and names its skill with `skill:`.

### Sections and impact bands

Each sectioned skill declares an ordered list of sections in its `SKILL.md`
`playbook.sections` (id, title, impact, a one-line summary and `open_when`),
and each member rule names its section in `section:`. A rule's priority is its
section's impact band plus its rank inside the section: CRITICAL 20-39, HIGH
40-59, MEDIUM 60-79, LOW 80-99. These bands replace the old kind-based priority
bands for members of sectioned skills. The skill's index renders one heading per
section (`### Mocking [CRITICAL]`) with a table of its active rules, and each
rule's title carries the `[IMPACT]` tag rendered from its section; a member of a
sectioned skill must not write the tag itself.

Every core skill that takes member rules declares sections, so a rule of yours
that joins one with `skill:` must now say where it goes:

- A repo-local rule (`playbook/rules/`) needs `section:` naming one of the
  skill's sections, or `playbook validate` fails, and `playbook sync` refuses to
  run:

      FAIL playbook/rules/risk-models-specific.md.j2: skill 'python-coding' declares sections, so its member rule needs 'section:'; declared sections: errors, shape, types, effects, async, pydantic, classes, functions, idioms

- Its `priority` must lie in that section's band:

      FAIL playbook/rules/risk-models-specific.md.j2: priority 30 is outside the band of section 'effects' (HIGH): expected 40-59

- An unknown section id fails the same way, listing the declared ones.
- A rule from an overlay or a bundled plugin without `section:` only warns: it
  is listed under an engine-generated "Other" section after the declared ones.
  With `section:` it is checked like a repo-local rule.
- `section:` on an always rule, or on a member of a skill that declares no
  sections, is an error.

v0.20 never asked for either key, so every repo-local rule written for v0.20
that joins a core skill fails `playbook validate` until it gets both (see
"Add skill: to your own scoped rules" for an example). A skill of your own may
declare sections as well; until it does, its members need neither key.

### 1. Lockfile schema 2

`.coding-agent-playbook.lock` is now `schema_version = 2`: every entry records
its provenance (`kind`, `artifact_id`, `source`, `adapter`), and with hooks on it
gains scoped entries (`scope = "json:/hooks/PreToolUse"`) for the managed
elements of `.claude/settings.json` plus an `executable` flag for copied hook
scripts (SPEC §14.4). A schema-1 lockfile still loads, its entries reading as
unknown provenance, and the first write-mode `playbook sync` rewrites it as
schema 2. Under the default `[output] commit = false` the lockfile is local
state, so there is nothing to do. Under `commit = true` that first sync changes
the committed lockfile once: commit it together with the engine bump.

A file written through an output dir linked out of the repo (`.claude/skills ->
/shared/skills`) now gets no entry: the lockfile never owns such output. Earlier
engines recorded it under its absolute, machine-specific path on every sync; the
first sync with this version leaves that entry out (and never deletes the
file). Under `commit = true`, commit that one-time lockfile change.

### 2. Run `playbook validate` first: `playbook sync` is validate-gated

Write-mode `playbook sync` and `playbook sync --check` now run the whole
`playbook validate` rule set before rendering. On any error they print its
`FAIL` lines, then

```text
playbook sync aborted; no files were written.
```

and exit 1, so content the engine would render wrongly (an unknown `applies_if`
fact, a broken eval-task reference, an invalid Agent Skill, a hook that breaks
its contract) never reaches disk. A repo whose content fails validate today
stops syncing on upgrade, the post-checkout auto-sync included, and its
generated output goes stale until the content is fixed. So run
`playbook validate` with your current engine and fix every `FAIL` before you
bump; after the bump, run it once more before the first sync, since v0.20 adds
the hook rules H1–H21 (SPEC §12.6). Warnings never stop a sync, and
`playbook sync --check-staged` (the pre-commit guard) is not gated.

`playbook validate` also runs without a `.coding-agent-playbook.toml` now: in an
engine or overlay checkout it validates the engine's content, the checkout's own
`src/<pkg>/resources/` and `playbook/`, and first names the consumer-config
checks it skips.

### 3. `[hooks]`: opt in through `playbook init`, or not at all

An engine upgrade never enables hooks. Without a `[hooks]` table every mode of
`playbook sync` renders byte for byte what v0.19 rendered (apart from the
Claude Code rules file, §12), and write mode prints one line:

```text
hooks available: add [hooks] enabled = true or re-run playbook init
```

To opt in, re-run `playbook init`: it asks `Enable assistant lifecycle hooks?
[Y/n]`, writes your answer as `[hooks] enabled` and keeps the rest of your
config. Or add `[hooks] enabled = true` by hand (README "Turning them on"). Then
run `playbook sync` once **interactively** on each machine: it pins the
worktree's Python interpreter under the git directory and asks the trust
questions for external handlers and execution Stop stages, which have no
non-interactive approve flag. To record a "no" and silence the notice, run
`playbook init --no-hooks` (it writes `enabled = false`). A scripted
`playbook init --non-interactive` re-run enables hooks unless the config already
sets `enabled`, so pass `--no-hooks` there to keep them off.

### 4. `.coding-agent-playbook.local.toml` never carries policy

`[hooks]` (with every `[hooks.<hook-id>]` and `[hooks.commit_convention]`),
`[guardrails]` and `[metrics]` are team policy: the rendered hooks, the CI twins
and the metrics gate must not depend on a gitignored file CI never sees. In
`.coding-agent-playbook.local.toml` they are **ignored**: `playbook sync` warns,
and `playbook validate` fails on a `[hooks]` or `[guardrails]` key there (H21).
Move such a table into the committed `.coding-agent-playbook.toml`. A developer
deviates at run time instead, through the hook-process environment
(`PLAYBOOK_HOOKS=off`, `PLAYBOOK_HOOKS_DISABLE=<ids>`, and their own command
launchers in `PLAYBOOK_HOOK_WRAPPER_PREFIXES=proxy,proxy run` rather than a
local `[hooks] wrapper_prefixes`). `playbook init` and `playbook check
--refresh` keep these tables when they rewrite the committed config, and never
write a local override into it.

### 5. `--no-run-tests` on the metrics pre-commit hooks

`[metrics] run_tests = true` used to make the `playbook-metrics` pre-commit hook
run your whole test suite on every commit. The engine's hook now runs
`playbook metrics --baseline git:HEAD --no-run-tests`, and the starter
`coding-agent-playbook-metrics` does too, so `run_tests` applies to CI and
manual runs only. Repos that reference the engine's `.pre-commit-hooks.yaml` get
this with the `rev:` bump. A `.pre-commit-config.yaml` that an older
`playbook init` wrote keeps its old `entry:` (init never rewrites a hook already
present), so add `--no-run-tests` there by hand if you set `run_tests = true`.
New hooks are not appended to an existing config either: copy
`playbook-secrets`, `playbook-coverage`, `playbook-commit-msg` and the others you
want from README "Pre-commit hooks" or SPEC §13.2.

### 6. `CoverageCheck` grades on the 0–1 score

`CoverageCheck()` now defaults to `warn=0.8`, which flags a file under 80%
coverage. The old default, `warn=80.0`, was a raw percentage that a normalized
0–1 score can never reach, so every file warned. Code that passes a percentage
explicitly must pass the 0–1 cutoff instead: `CoverageCheck(warn=80.0)` becomes
`CoverageCheck(warn=0.8)`. Eval-task `[gate]` thresholds were already 0–1
(v0.13) and need nothing.

### 7. New metrics, and how to select them

| Metric | Measures | Selected |
| --- | --- | --- |
| `ruff_violations` | ruff findings per file and code family (`quality`: C901, PLR0911, PLR0912, PLR0913, PLR0915; `docstrings`: D100–D107), through `ruff` on `PATH` as a subprocess | opt-in, by name |
| `file_sloc` | source lines per file (needs the `metrics` extra, radon) | opt-in, by name |
| `docstring_example` | whether a public function's docstring carries a usage example | opt-in, by name |
| `diff_coverage` | the share of the changed executable lines the suite ran (fails below 80%) | with `--run-tests` and a `git:` baseline |

The three opt-in metrics are selected only by name, never by default or through
a family, so an upgrade leaves every existing static result byte-stable:

```toml
[metrics]
extend_select = ["ruff_violations", "file_sloc"]
```

or `playbook metrics --extend-select ruff_violations,file_sloc`. `diff_coverage`
is a default member of the `testing` family: `playbook metrics --run-tests
--baseline git:<ref>` now grades it as well, which can fail a change whose new
lines are untested. Keep the old result with `ignore = ["diff_coverage"]`. The
other new `[metrics]` keys are `select`, `ignore`, `exclude` (default
`["**/eval_tasks/*/setup/**"]`; a list replaces it), `git_timeout_s`,
`test_timeout_s` and the `[metrics.ruff_violations]` sub-table (SPEC §7.1.1).
The README's "Clean Code for AI Agents preset" combines them.

### 8. PEP 503 dependency names: a one-time `detector_cache` change

The detector now normalizes dependency names the way package indexes compare
them (PEP 503): lower case, with every run of `-`, `_` and `.` turned into one
`-`, so `Foo_Bar` → `foo-bar` (names used to be lower-cased only). The detector,
the `has_dev_dependency` predicate, dependency-allowlist-guard and
`playbook check-deps` share this one normalization. Two one-time effects
(OQ-36):

- the `[detector_cache]` tables of `.coding-agent-playbook.toml` change their
  keys for such a name the next time `playbook init` or
  `playbook check --refresh` rewrites them: commit that diff;
- a dependency declared as `pytest_asyncio` now matches the `pytest-asyncio`
  the detector knows, so a rule or prompt gated on it can start to apply.
  Spell `applies_if` names in the normalized form
  (`has_framework: ["pytest-asyncio"]`).

### 10. Out-of-tree adapters: the hook members, and `stale_outputs`

`Adapter` gains seven hook members. Each is a concrete default, like
`write_skill`, so an adapter written before hooks keeps working unchanged and
is an advisory-only target:

- `hook_support` (class attribute, default empty): canonical event → the
  decisions this adapter renders natively; empty means advisory-only.
- `shared_outputs` (class attribute): files co-owned with the user, such as
  `.claude/settings.json`, which get scoped lock entries for their managed
  elements and never a whole-file one.
- `runtime_outputs` (class attribute): hook plumbing that `finalize` writes
  whole, locked as `kind = "runtime"`. Sync refuses to write one over a user
  file of the same name (no sentinel on line 1), over a hard link (even a
  sentinel-tagged one) or through a symlink: it exits 1 naming the file before
  any adapter writes.
- `planned_runtime_outputs(hooks)`: which `runtime_outputs` this sync's
  `finalize` will write, for that check. The default (every declared one once a
  hook lists your adapter in `supports`) is safe; override it only to name
  exactly what `finalize` writes.
- `begin_sync(repo_root, prior_lock, *, hooks_config=None)`: called once per
  sync before any `write_*`, always with the real repository, `--check` included.
- `write_hook(hook, repo_root)`: called for every on hook, after the skills. The
  default degrades the hook to its advisory rule (`guardrail-<id>`, priority 30)
  through your own `write_rule`, so with hooks on your `write_rule` receives one
  such rule per on hook whose body is not blank. Override `write_hook` to route
  or drop them.
- `managed_lock_entries()`: the scoped lock entries of the last `finalize`
  (default `[]`).

Sync calls them in one order per adapter: `begin_sync`, the `write_rule` /
`write_prompt` / `write_skill` loops, `write_hook`, `finalize`, then
`managed_lock_entries`; `cleanup_stale` still runs after every adapter's
`finalize` (SPEC §10.1).

One more optional class attribute, `native_skills_root` (default `None`): an
adapter whose `write_skill` delegates to the shared `SkillWriter` names its root
there (`".claude/skills"`), so `playbook sync --check` explains a file missing
inside `<root>/<id>/` the way that writer settles it (SPEC §10.8, §12.3). Leave
it unset otherwise.

#### Override `stale_outputs`, not `cleanup_stale`

`playbook sync --check` now reports orphans (SPEC §12.3), so it must know what
write mode would delete without deleting it. `Adapter.stale_outputs(written_paths,
repo_root) -> list[Path]` is that read-only answer and the **only** override point
for staleness; `Adapter.cleanup_stale` deletes exactly what it returns. Who needs
to act: authors of third-party adapters (the `coding_agent_playbook.adapters`
entry-point group) that override `cleanup_stale`. Rule/prompt/skill authors and
built-in adapter users need nothing.

```python
# before (SPEC §10.1 up to v0.19)
def cleanup_stale(self, written_paths, repo_root):
    return self._default_cleanup(written_paths, repo_root)


# after: report, never delete; the ABC's cleanup_stale deletes what you return
def stale_outputs(self, written_paths, repo_root):
    return self._stale_by_sentinel(written_paths, repo_root)
```

An adapter that still overrides only `cleanup_stale` keeps working in write mode
(`_default_cleanup` is kept, deprecated), but `--check` prints
`warning: adapter '<name>' overrides cleanup_stale() but not stale_outputs()` and
reports no sentinel orphans for it. Scan helpers to reuse: `_stale_by_sentinel`
(the default), `_scan_targets` (each file once, never a symlink or a secret path)
and `_carries_sentinel` (bounded, anchored sentinel check).

### 12. Claude Code rules move to `.claude/rules/coding-agent-playbook.md`

The `claude_code` adapter now writes every rule section (and, with hooks on, the
advisories of hooks Claude Code cannot enforce and the §9 heartbeat line) to one
rules file, `.claude/rules/coding-agent-playbook.md`, and `.claude/CLAUDE.md`
becomes a four-line generated stub with no rules in it. Claude Code loads a
`.claude/rules/` file without `paths:` frontmatter natively, at launch and with
the same priority as `.claude/CLAUDE.md`, so Claude sees the same rules as
before; the sections are unchanged, and the rule sections are still
byte-identical to `AGENTS.md`'s (SPEC §10.3.1), up to line endings: both
Claude Code files are now written LF on every platform, while `AGENTS.md` stays
CRLF on Windows.

**Why.** OpenCode v1, run at or above the repo root, attaches
`.claude/CLAUDE.md` the first time its read tool opens a file under `.claude/` in
a session, so it loaded the rules twice (`AGENTS.md` plus that copy, again after
each compaction, in each subagent session and on each `@`-mention) and saw the
Claude-only heartbeat line. Neither OpenCode v1 (1.19.3) nor v2 (dev
`24c7f7a`) discovers `.claude/rules/` on its own (v1 looks up files named
`AGENTS.md`, `CLAUDE.md` or `CONTEXT.md`; v2 only `AGENTS.md`; v2's `.claude/`
compatibility reads only `skills/`), so that duplicate is gone; only an `opencode.json`
`instructions` entry you add, such as `.claude/rules/*.md`, would load the rules
file, next to `AGENTS.md`. The stub must stay: in Claude Code's default
`claude-md-or-agents-md` mode (v2.1.277+), a `.claude/CLAUDE.md` stops Claude
Code from also reading the root `AGENTS.md`, and a rules file does not. (With
Project instructions set to `claude-md-and-agents-md`, Claude reads `AGENTS.md`
and the rules file, as it read `AGENTS.md` and the full `.claude/CLAUDE.md`
before.)

What the next `playbook sync` (or the post-checkout / post-merge hook) does:

- It rewrites `.claude/CLAUDE.md` to the stub, writes the rules file and
  records both in the lockfile. Under the default `[output] commit = false` both
  stay local; the managed `.gitignore` block gains
  `/.claude/rules/coding-agent-playbook.md`, so commit that `.gitignore` change
  once. Under `commit = true`, commit both files and
  `.coding-agent-playbook.lock`; until then `playbook sync --check` on a fresh
  checkout (CI) reports them as drift.
- As before, sync overwrites hand edits of `.claude/CLAUDE.md`, and now of the
  rules file too; with hooks on, guard-generated-outputs denies an agent's edit
  of either. Change rules in `playbook/rules/`, and keep your own notes in a
  file the engine does not own, such as your own `.claude/rules/<name>.md`.
- A file of yours already named `.claude/rules/coding-agent-playbook.md` (one
  without the generated sentinel on line 1) is refused, never overwritten, and
  so is a hard link at that path (even of the generated file: writing it whole
  would change the other name too) or a symlinked `.claude` or `.claude/rules`:
  sync exits 1 before writing anything, with
  `error: .claude/rules/coding-agent-playbook.md: <reason>` (`--check` prints
  `Cannot verify …`). Rename your file, delete the extra hard-linked name, or
  replace the link with a real directory, then re-run `playbook sync`. The
  hook launcher and the OpenCode plugin refuse a hard link the same way.
- `.claude/CLAUDE.md` is still overwritten whatever regular file is there, but
  never through a symlink or a hard link: a link such as
  `.claude/CLAUDE.md -> ../AGENTS.md`, or the same file hard-linked to
  `AGENTS.md` (common on Windows), would turn `AGENTS.md` into the stub for
  every other tool, so sync exits 1 before writing anything, with
  `error: .claude/CLAUDE.md: it is a symbolic link, …` (or `it is a hard link
  shared with another file, …`). A directory or other non-regular file there is
  refused the same way (`it is not a regular file`). Delete the link, or move
  what is there (Claude Code reads the rules file instead), then re-run
  `playbook sync`.
- Every other `.claude/rules/` file stays yours: the engine owns exactly
  `coding-agent-playbook.md` there and never reads, rewrites, gitignores or
  deletes any other file.
- Rules are still unscoped: the rules file has no `paths:` frontmatter, so every
  rule loads in full, as before; a rule's globs stay advisory.
- An OpenCode v1 user who set `OPENCODE_DISABLE_CLAUDE_CODE_PROMPT=1` for the
  duplicate may unset it once synced (it also hid the global
  `~/.claude/CLAUDE.md` from OpenCode).

Not changed: `AGENTS.md`, `.continue/`, `.opencode/` and `shared_skills/`
output (so OpenCode v2, Codex and Cursor see no difference; GitHub Copilot
CLI, which also reads `.claude/CLAUDE.md` next to `AGENTS.md`, now gets the stub
instead of a second copy of the rules, and VS Code Copilot Chat with
Claude-format instructions on finds them in
`.claude/rules/coding-agent-playbook.md` instead), prompts
(`.claude/commands/`) and skills (`.claude/skills/`), and
`playbook render --format claude_md_section` (the format name and its bytes).

### 1. `packs` → bundled plugins, and the deprecated alias

<!-- module-moves: keep -->

### 2. The new warning lines

Every command that loads the config (`sync`, `check`, `validate`, `render`,
`eval`, and `init`'s final sync) prints exactly one stderr line per deprecated


```text
warning: --overlays: '<old>' is deprecated; use '<new>'
```

### 4. New preflight reasons and hint

A bundled-plugin name in `overlays_enabled` is now checked against
`content/plugins/<name>/` (now `catalog/plugins/<name>/`) and never imported. `sync`, `validate`, `check` and

| Entry | Before | Now |
|---|---|---|
| Unknown plugin, e.g. `coding_agent_playbook.plugins.superpower` | `not importable` | `no such bundled plugin` |

## v0.13 — Task config v2 (gate / rubric / verdict / aggregate)

The eval **task config** is redesigned (Tracks C1–C8). The old
`[expected]`/`[metrics]`/`[rubric]` triple is replaced by a **layered**,
expression-composed format; this is a destructive cutover with **no backward
compat**. Authoritative design: `specs/pr2b-task-config.md`.

### TL;DR — who needs to do anything

| You are… | Migration |
|---|---|
| An **eval-task author** (`task.toml`) | **Rewrite** the `[expected]`/`[metrics]`/`[rubric]` blocks into `[gate]`/`[rubric]`/`[verdict]`. See the mapping below. |
| A **`playbook eval --run` user** | **Nothing** (same CLI; `--full-scoring` unchanged). |
| A **`playbook metrics` user** | **Nothing.** The standalone gate + its `[metrics]` engine config in `.coding-agent-playbook.toml` are unchanged. |
| An **out-of-tree `Metric` author** | Add a `normalizer` (`higher_is_worse` is gone). See below. |
| An **out-of-tree check / gate author** | Register under the new `coding_agent_playbook.checks` / `coding_agent_playbook.gates` groups. |

### 1. Block mapping (`[expected]`/`[metrics]`/`[rubric]` → `[gate]`/`[rubric]`)

There is **no `[expected]` block** and **no top-level `[metrics]` task block**.
File predicates and metric thresholds are all `[gate.bind]` *handles* (a handle is
a named entry the `[gate].expr` boolean expression references). Thresholds are now
**0–1 normalized** cutoffs, not raw units.

| Old | New (`[gate.bind]` handle) |
|---|---|
| `[expected] files_created = ["t.py"]` | `made = { check = "file_exists", path = "t.py" }` |
| `[expected] files_must_contain = [{path="t.py", pattern="def test"}]` | `has = { check = "file_contains", path = "t.py", pattern = "def test" }` |
| `[expected] files_unchanged = ["src/a.py"]` | `keep = { check = "file_unchanged", path = "src/a.py" }` |
| `[expected] files_forbidden = ["x/"]` | `nox = { check = "file_forbidden", path = "x/" }` |
| `[metrics.thresholds] cyclomatic_complexity = {fail=20}` | `cc = { check = "threshold", metric = "cyclomatic_complexity", fail = 0.5 }` *(0–1, normalized)* |
| `[metrics.regression] coverage = {max_worsening=0}` | `cov = { check = "non_regression", metric = "coverage", max_worsening = 0.0 }` |

Then compose the handles with a `[gate].expr` and (when omitted on a single-handle
layer) it defaults to that handle's name:

```toml
# OLD
[expected]
files_created = ["tests/test_calc.py"]
files_unchanged = ["src/calc.py"]
[metrics.regression]
coverage = { max_worsening = 0 }
[rubric]
criteria = ["Covers all branches", "No mocking"]
weights  = [0.6, 0.4]

# NEW
[gate]
expr = "made and keep and cov"
[gate.bind]
made = { check = "file_exists",    path = "tests/test_calc.py" }
keep = { check = "file_unchanged", path = "src/calc.py" }
cov  = { check = "non_regression", metric = "coverage", max_worsening = 0.0 }
[rubric]
expr = "quality"
[rubric.bind]
quality = { fail = 0.5, rubric = [
  { judge = "Covers all branches", weight = 0.6 },
  { judge = "No mocking",          weight = 0.4 },
] }
[verdict]
trial = "gate and rubric"   # the default; may be omitted
```

A `[rubric] ref = "name"` (named rubric) becomes a `[rubric.bind]` handle
`{ ref = "name" }`; a `[rubric] criteria/weights` becomes a `{ rubric = [{judge,weight},…] }`
group (weights still sum to 1.0), thresholded to a boolean by `fail`.

### 2. `higher_is_worse` → a per-`Metric` `Normalizer`; thresholds are 0–1

`higher_is_worse` is **deleted**. Every `Metric` now owns a `Normalizer`
(`grading/normalizer.py`) mapping its raw value to a **0–1 goodness** where
higher is always better, folding the metric's native direction in:

```python
# before
class MyMetric(Metric):
    higher_is_worse = True  # larger raw = worse


# after
from coding_agent_playbook.grading.normalizer import RampNormalizer


class MyMetric(Metric):
    normalizer = RampNormalizer(good=5, bad=20)  # 5 -> 1.0, 20 -> 0.0 (worse-when-larger)
```

Use `RampNormalizer(good, bad)` for an unbounded metric (the same class serves
both directions — pick `good < bad` for worse-when-larger, `good > bad` for
better-when-larger), `PercentNormalizer()` for a 0–100 metric (coverage, MI), or
`Identity()` for one already on 0–1 (test pass rate, judge scores). Because grading
is on the normalized score, **every threshold** (`warn`, `fail`, `max_worsening`)
is now a **0–1 cutoff**, not a raw value: a CC `fail=20` becomes `fail≈0.25`,
coverage `warn=80` becomes `warn=0.8`.

### 3. New entry-point groups: `coding_agent_playbook.checks` / `.gates`

A task `{ check = "<id>", … }` handle resolves through the **checks** registry; a
gate-layer `{ ref = "<name>" }` resolves through the new **gates** registry:

```toml
# pyproject.toml
[project.entry-points."coding_agent_playbook.checks"]
my_check = "my_pkg.checks:MyCheck"          # a Check factory; @register_check("my_check")
[project.entry-points."coding_agent_playbook.gates"]
must_touch_tests = "my_pkg.gates:must_touch_tests"   # a () -> Check factory; @register_gate("must_touch_tests")
```

The `coding_agent_playbook.rubrics` group (named rubrics, `@register_rubric`) is
unchanged. In-tree builtins win on a name clash; the engine ships no builtin
gates or rubrics.

### 4. A judged criterion is a metric (`JudgeMetric`)

You can now run `threshold` / `non_regression` over a **judge criterion**, not just
a registered metric: `{ check = "non_regression", judge = "overall quality", max_worsening = 0.1 }`
adapts the judge as a `JudgeMetric` (0–1, `Identity`-normalized) so the same
regression machinery applies. (The weighted `{ rubric = [...] }` group is the other
judged shape and is unchanged.)

### 5. Cross-trial reliability (`[aggregate]`, optional)

A new optional `[aggregate]` layer grades `pass@k` / `pass^k` across trials; omit
it and a task runs a single trial exactly as before:

```toml
[aggregate]
expr = "reliable"
[aggregate.bind]
reliable = { metric = "pass_at_k", k = 5, over = "verdict", fail = 0.9 }
```

The runner runs `N = max(k)` trials and the aggregate composes them.

### Not changed (v0.13)

- The `playbook metrics` CLI + its `[metrics]` engine config in `.coding-agent-playbook.toml`.
- The metric algorithms (CC/WMC/LCOM4/DIT/CBO≈/MI, `coverage`/`test_pass_rate`) and the non-regression semantics (now on the normalized score).
- The `radon` optional extra, still backing `maintainability_index` only.
- The `coding_agent_playbook.metrics` / `coding_agent_playbook.rubrics` / `coding_agent_playbook.judges` / `coding_agent_playbook.runners` entry-point groups.

## v0.12 — `Evaluator` → `Metric` / `Check` / `Rubric` (PR R6)

The code-quality evaluator subsystem (SPEC §21) was refactored from one fused
`Evaluator` ABC + a free `grade()` function into **three single-responsibility
abstractions**: `Metric` (measure) → `Check` (grade) → `Rubric` (aggregate).
Authoritative design: `specs/prR6-check-rubric.md`.

### TL;DR — who needs to do anything

| You are… | Migration |
|---|---|
| An **eval-task author** (writing `task.toml` with `[expected]`/`[metrics]`/`[rubric]`) | **Nothing.** The authored TOML is unchanged. |
| A **`playbook metrics` / `playbook eval --run` user** | **Nothing.** Same commands, same flags (plus the new `--full-scoring` on `eval --run`). |
| An **out-of-tree extender** registering a custom evaluator | **Port it** — see below. |

The only breaking change is for **out-of-tree packages** that registered a custom
`Evaluator` or called the engine's evaluator API directly. The authored task
format and the CLI are unchanged.

### 1. `Evaluator` subclass → `Metric` subclass

Drop the grading-side and value-shape fields; keep (and rename) the measurement:

| Old `Evaluator` | New `Metric` |
|---|---|
| `class MyMetric(Evaluator)` | `class MyMetric(Metric)` |
| `evaluate(self, ctx) -> list[Measurement]` | **`measure(self, ctx) -> list[Measurement]`** (renamed; same body) |
| `value_kind = ValueKind.NUMERIC` | **deleted** — a metric is always a raw measurement |
| `to_score(self, value, policy)` | **deleted** — normalization is the `Check`'s job |
| `default_absolute` / `default_regression` / `default_weight` | **deleted** — grading policy lives on the `Check`, not the metric |
| `name`, `scope`, `requires`, `needs_project` | **kept, unchanged** |
| `higher_is_worse` | **kept in v0.12; deleted in v0.13** → a `Normalizer` (see the v0.13 section above) |
| `available(self, ctx)` | **kept** (default still gates on deps + the needed ctx slot) |

<!-- module-moves: keep -->
```python
# before
from coding_agent_playbook.evaluators.registry import Evaluator, register_evaluator
from coding_agent_playbook.evaluators.scope import Scope, ValueKind, Determinism


@register_evaluator
class MyMetric(Evaluator):
    name = "my_metric"
    scope = Scope.FUNCTION
    value_kind = ValueKind.NUMERIC
    determinism = Determinism.DETERMINISTIC
    higher_is_worse = True
    default_absolute = AbsoluteThreshold(warn=10, fail=20)
    default_regression = RegressionPolicy(max_worsening=0)

    def evaluate(self, ctx): ...
    def to_score(self, value, policy): ...


# after
from coding_agent_playbook.evaluators.metric import Metric, register_metric
from coding_agent_playbook.evaluators.scope import Scope


@register_metric
class MyMetric(Metric):
    name = "my_metric"
    scope = Scope.FUNCTION
    higher_is_worse = True  # v0.12 only — v0.13 replaces this with a Normalizer

    def measure(self, ctx): ...  # was evaluate(); same body
```
<!-- module-moves: end-keep -->

> **v0.13 update:** drop `higher_is_worse` and declare a `normalizer` instead (see
> the v0.13 section, step 2).

The default warn/fail bounds and regression tolerance that used to live on the
metric now live in `metrics_gate/policy.py::METRIC_DEFAULTS` (for the builtins) and,
for your metric, are supplied by whoever builds the `Check` — a `[metrics]`
config override or a `ThresholdCheck(...)` you construct.

### 2. Entry-point group rename: `…​.evaluators` → `…​.metrics`

<!-- module-moves: keep -->
```toml
# pyproject.toml — before
[project.entry-points."coding_agent_playbook.evaluators"]
my_metric = "my_pkg.metrics:MyMetric"

# after
[project.entry-points."coding_agent_playbook.metrics"]
my_metric = "my_pkg.metrics:MyMetric"
```
<!-- module-moves: end-keep -->

In-tree builtins still win on a name clash.

### 3. Custom graders register under the new `coding_agent_playbook.checks`

A custom *grading strategy* (beyond the built-in threshold / non-regression /
file / judge checks) is now a `Check`, registered under the **new**
`coding_agent_playbook.checks` entry-point group:

```toml
[project.entry-points."coding_agent_playbook.checks"]
my_check = "my_pkg.checks:MyCheck"
```

A `Check` implements `grade(self, ctx, measurements) -> CheckResult` and sets
`id`, `weight`, `required`, `determinism`, and `cost: CostTier`. See
`grading/check.py` (`ThresholdCheck`/`NonRegressionCheck`),
`grading/judged.py` and `grading/compose.py` (judge/compose) and `evals/checks/files.py` (file) for the
built-in shapes.

### 4. `grade()` → `Rubric.evaluate`

If you called the engine's grading function directly, build a `Rubric` and call
`evaluate` instead. The `extra_evaluators` side-channel is gone — every check
(metric-backed, file, judged, composed) is just an entry in the rubric's ordered
check list:

<!-- module-moves: keep -->
```python
# before
from coding_agent_playbook.evaluators.grade import grade

report = grade(candidate, baseline, policy, extra_evaluators={name: inst})

# after
from coding_agent_playbook.evaluators.rubric import Rubric
from coding_agent_playbook.evaluators.check import MeasurementSet

rubric = Rubric([check1, check2, ...])  # ordered list of Checks
report = rubric.evaluate(ctx, MeasurementSet(candidate, baseline))
```
<!-- module-moves: end-keep -->

Both return an `EvaluationReport` (`passed`, `composite`, `findings`, `checks`).
To build the metric-backed checks for a `[metrics]`-style config, reuse the
shared factory `metrics_gate/policy.py::metric_check(name, config)` (the same one
`playbook metrics` and `rubric_for_task` use), so your gate honours identical
per-metric policy.

### 5. Deleted symbols (no compatibility shim)

<!-- module-moves: keep -->
`Evaluator`, `evaluators/registry.py`, `evaluators/grade.py` (`grade()`),
`evaluators/expected.py`, `evaluators/judged.py` (`JudgedCriterion`),
`ValueKind`, `to_score`, the `default_absolute`/`default_regression`/`default_weight`
fields, and `evals/task.py::evaluators_for_task` are **removed**. Their
replacements: the file checks live in `evaluators/checks/files.py`, the judged
check in `evaluators/checks/judged.py` (`JudgeCheck`), and the task compiler is
`evals/task.py::rubric_for_task` (returns a `Rubric`).
