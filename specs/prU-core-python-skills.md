# PR U: vendor upstream Python guidance into core skills

Status: ready for implementation once the owner says to start (grilling rounds 1-5 done; per-file mapping verified: 171 rules, 0 check errors; 47 tickets).

Sources:

- pbp: the "python-best-practices" agent skills by Ludo Technologies LLC (MIT), tag v0.8.0, commit fa0d3f58afb8bf56c028bb559e0e7bc1538e079a.
- pca: the "python-clean-architecture" Claude Code plugin by MKToronto (MIT), commit 9d627ca7bedbe0bb9e2fcf3c83d81814a6133dce (16 commits after v0.8.1).

## Decisions

- **D1 Vendor, do not distill.** Core copies the upstream text as its base and adapts it: engine frontmatter, the repo's toolchain, no URLs. Each source's MIT notice is kept and ATTRIBUTIONS lists the changes. This reverses the "all text written fresh" policy in `catalog/core/ATTRIBUTIONS.md`; the glossary's **Vendored content** now covers core.
- **D2 Fold `python_design` into core.** The bundled plugin is deleted. Its three original stdlib scripts (`detect_smells.py`, `lcom4_clusters.py`, `layer_map.py`) move into the new core skills.
- **D3 One topic per file at pbp size** (at most 100 rendered lines, see D20). pca's long references are split into several rules each. Result of the verified mapping: 171 rule files across seven skills (28 today); amended in round 5 (D46.6), because D26 and the D20 splits drive the count. If cuts are ever needed, they come from the LOW "Specialized patterns" section, not by merging topics.
- **D4 Eight core skills:** `python-coding`, `python-testing`, `python-tooling`, `ml-data`, `playbook-guardrails` (existing names, hyphenated), plus new `web-application`, `design-patterns` and `python-architecture`.
- **D5 Rules live in their skill's `rules/` directory**, in the catalog source and in the rendered output. `references/` holds free-form long-form documents (no gate, no priority). `skill:` stays only for rules that come from another layer (overlay, bundled plugin, consumer repo) and join a skill.
- **D6 Precedence when content overlaps:** engine decisions > pbp > pca. pbp's rule file is the skeleton; pca adds examples and notes; an existing engine point that encodes a past decision wins over both (uv; Protocol or Callable seams first; timeouts and bounded, transient-only retries; money never `float`; unmapped domain errors become HTTP 500). Engine rules that cover several topics are split to pbp granularity.
- **D7 Rule format:** engine frontmatter (`id`, `description`, `scope`, `applies_if`, `priority`, `globs`, `lint_codes`, `tags`, ...) with pbp's body sections: `# Title [IMPACT]`, Description, Bad Example, Good Example, Notes. pbp's `## References` link lists are dropped.
- **D8 Controls:** priority sets the order of each skill's index (CRITICAL first); `applies_if` gates on detector facts decide which rules render; `globs` drive skill nudges; `lint_codes` tie ruff codes to a rule. Gate a whole rule with `applies_if` first; use a `.md.j2` template only when a detector fact changes part of a rule's text.
- **D9 pca commands become content, not prompts.** Their checklists go into skill rules, and they are merged into the existing prompts where they overlap (`review-architecture`, `refactor`, `make-testable`, `characterize`). No new prompts in this change.
- **D10 Toolchain:** pbp's tooling rules are rewritten to the repo's standards (uv, the consumer repo's own ruff and mypy configuration). `pyscn` and pbp's fixed linter settings are dropped.
- **D11 Pins:** the two commits above. A re-pin is a reviewed PR that diffs two upstream commits and replays the list of changes.
- **D12 ADRs:** ADR 0004 "Upstream Python guidance is vendored into core" and ADR 0005 "Member rules live in their skill's `rules/` directory" (amends ADR 0001).
- **D13 Delivery:** this spec, then tickets on one integration branch. Lane 0 changes the engine (rules inside skills, rendered `rules/`, moving the 26 existing scoped rules). One content lane per skill runs in parallel worktrees, plus a docs lane; the `python_design` removal is already done and lands in wave 0. One final PR into main; the full CI gate runs only on that final merge.
- **D14 Skill boundaries by scale:** `python-architecture` covers relations between modules (layers, import direction, composition root, ports, project organization, DDD, persistence strategy, testing across layer seams). `design-patterns` covers the shape of code inside a module (Pythonic forms of the classic patterns, principles and GRASP, smells, quality checklist, refactoring, splitting god classes). `python-coding` covers line- and function-level idioms.
- **D15 Gray zones:** repository, unit of work, CQRS and event sourcing go to `python-architecture`. Passing dependencies as parameters stays in `python-coding`; wiring them at the composition root goes to `python-architecture`. pca's retry pattern merges into the existing `python-retries-and-timeouts` rule in `python-coding`. pbp's SOLID and composition-over-inheritance rules go to `design-patterns`; `python-coding` keeps the concrete Protocol, dataclass and property rules.

- **D16 Phase 0 timing:** skills and rules land before the v0.1.0 tag; prompts' `includes_rules` and new `lint_codes` stay frozen until after the pilot. D9's prompt merges become a post-pilot follow-up.
- **D17 Sections and priority:** each skill's `SKILL.md` declares an ordered list of sections (title, impact, one-line summary); each member rule names its `section:`; the generated index renders one heading per section (`### Mocking [CRITICAL]`) with a table of its active rules. Priority = impact band + rank within the section: CRITICAL 20-39, HIGH 40-59, MEDIUM 60-79, LOW 80-99 (replaces the kind bands of SPEC's priority policy). The "Covers" clause names sections, not rules.
- **D18 Budgets:** the per-skill description cap stays 300 characters; the core total rises from 2,000 to 2,400 and the listing cap (core plus each bundled plugin) from 6,000 to 6,500.
- **D19 MIT notice:** each core skill holding vendored text ships byte-identical `references/LICENSE.python-best-practices` and/or `references/LICENSE.python-clean-architecture`; the self-containment test exempts exactly those files; Continue's gap is accepted with a README note.
- **D20 Rule size:** the existing cap holds, 100 rendered lines and 750 words. D3 reads "one topic per file, at most 100 lines"; longer material is split or becomes a reference.
- **D21 Ids and validation:** a split keeps the old id on the piece that keeps the old topic (hook links, prompt lists, lint codes keep working). Retired ids: `python-performance-idioms`, `python-classes-and-protocols`, `ml-dtypes-and-typing`, `ml-reproducibility-and-testing`. New prefixes: `design-`, `arch-`, `web-`, and `sqlalchemy-`, `alembic-`, `httpx-`, `ruff-`, `mypy-` where one tool owns the topic. New checks: file name equals id; duplicate ids in one layer fail; an unknown frontmatter key is a validation error naming the file; `scope` and `priority` (0-99) are validated; a rule inside `skills/x/rules/` must not declare another `skill:`. The two always rules stay in `catalog/core/rules/`.
- **D22 agent_harness:** its tree also gets `rules/` inside each skill; `import-harness` follows.
- **D23 Detector gates:** a generic `has_dependency` / `any_dependency` predicate (runtime or dev). `web-application` rules gate on any web framework (fastapi, flask, django, starlette); its DB rules also need sqlalchemy or alembic. A repo with SQLAlchemy and no web framework gets `python-architecture`'s persistence rules.
- **D24 Pydantic:** general rules (validation at I/O boundaries, typed settings) go to `python-coding`, gated on pydantic; its description drops "library-agnostic". Web-specific rules (separate request and response schemas) go to `web-application`.
- **D25 pca vs python_design:** pca's text is the base, with python_design's conflict resolutions applied. python_design's `worked-example.md` becomes a `python-architecture` reference; its three scripts and their tests return under the new skills. pca's hotel example app is not shipped; pca's flawed `testing/` bookstore is a seed for a later eval task.
- **D26 Patterns:** one rule file per pattern (at most 100 lines); LOW-impact patterns sort last. The long OOP-to-functional walkthroughs (strategy, abstract factory, bridge, command, observer) become references their rule points to.
- **D27 Engine decisions vs upstream:** (1) web apps build the DB engine in the app factory or lifespan; scripts and CLIs may still build it at import time. (2) FastAPI dependency aliases use concrete `AsyncSession` / `httpx.AsyncClient` at the route edge; Protocols are for the app's own ports. (3) Unit tests use fakes; persistence and endpoint tests use the real engine in a rolled-back transaction. (4) Async tests use the plugin the repo has; with none, anyio's marker where FastAPI, Starlette or httpx is present (Starlette added in round 5, D43), else pytest-asyncio (Jinja branch on detector facts). (5) A request-scoped `ContextVar` is an explicit exception to "no module-level state".
- **D28 Self-contained web rules:** no rule depends on another rule's example; pbp's shared invoice example is repeated or replaced per rule.
- **D29 uv stays gated** on `package_manager: uv`; other repos get no migration push.
- **D30 Prompt-included rule bodies may change.** The bodies of `pytest`, `python-typing`, `python-error-handling`, `python-dependency-injection`, `python-pure-core` and `ml-serialization-security` change with the merge. Amended in round 5 (D37): no paid eval run in this effort; the comparison becomes an opt-in option, and the final merge does not wait for it.
- **D31 Provenance:** `catalog/core/ATTRIBUTIONS.md` holds one mapping table per source (upstream file -> core rules and references, or DROP with a reason). A CI test checks that every core file with vendored text is listed, every listed file exists, and the pins match D11. The "written fresh" sentences and the `bf64c51` pin go; the literal-token bans on dropped recommendations stay.
- **D32 Skill files:** `SKILL.md` = pbp's intro and adapted Quick Reference, then the generated section index. "See Also" becomes plain-text skill names (no cross-skill links). pbp's `README.md` and `metadata.json` are dropped; `_template.md` becomes a "Writing a rule" section in `catalog/README.md`. The `[IMPACT]` tag in a rule's title is rendered from its section, never authored; `mock-monkeypatch` goes to a HIGH section.
- **D33 Tracking:** a GitHub tracker issue and one issue per ticket, branch `integration/core-python-skills`, about 6 parallel lanes, lane 0 first; each ticket implemented in its own fresh-context subagent running the `/mattpocock-skills:implement` skill (TDD at seams, two-axis code review), tickets of a wave in parallel, at medium effort (owner's instruction, 2026-10-21). Issues are created only once the owner says to start.
- **D34 Lane done:** CI green plus a review sub-agent that compares each new rule with its upstream source and this decision list (adapted, every engine decision applied, nothing lost without a DROP row); findings fixed before the lane merges.
- **D35 Always-loaded context:** lane 0 measures the "Where guidance lives" map with eight skills; if a cap (800 words for always rules, 1,500 for `AGENTS.md`) would be exceeded, the map lines get shorter and the caps stay.
- **D36 Forge overlap:** lane 0's check rejects a core scoped rule outside a skill's `rules/`, with a hint saying where to move it; whichever of this work and forge (#170) merges second rebases and moves its files.

Round 5 (after the per-file mapping):

- **D37 Evals are opt-in (amends D30).** No paid eval run in this effort. Ticket F-01 adds one opt-in way, off by default, to compare the eval tasks of the seven prompts whose included rule bodies change (review, refactor, make-testable, review-architecture, generate-tests, characterize, security-review) on a base ref and on HEAD. Defaults: 3 samples per task on each ref with the same model; a regression is a mean score drop above 0.05 on any task, or a task that passes on the base failing in 2 of 3 samples. Running it needs the owner's credentials and costs money; it is not a merge gate.
- **D38 Example URLs:** only reserved hosts (example.com, .org, .net and their subdomains; `*.test`, `*.example`, `*.invalid`; `localhost`; the bare host `test`), only inside fenced code blocks under `catalog/core/skills/`. Prose stays URL-free.
- **D39 Stack-neutral SQL parameters:** a new ungated `python-coding` rule, `python-parameterized-queries` (driver placeholders, allow-listed identifiers), next to web-application's `sqlalchemy-bound-parameters`.
- **D40 Python versions through Jinja:** example code targets Python 3.10 as the lowest branch. Where the idiomatic form differs on a newer Python (Self, StrEnum, datetime.UTC, TaskGroup, asyncio.timeout, ExceptionGroup, tomllib, PEP 695), the rule is a `.md.j2` that branches on a new numeric helper `python_at_least("3.11")`, instead of being hidden by a version gate. `applies_if: python_version` stays only where the topic does not exist below that version (`match`: >=3.10). `python-typing`, `python-async`, `python-async-tasks` and `python-async-fanout` lose their >=3.11 gate. Lane 0 adds the helper, fixes `typing.md.j2`'s string comparison, and renders every core template across a fact matrix with the D20 caps on every branch.
- **D41 Skill nudges:** one shared test-file glob set for test-related rules (`**/test_*.py`, `**/*_test.py`, `**/tests/**/*.py`, `**/conftest.py`, `**/fakes.py`); a nudge ranks matching skills by their most specific glob and keeps the five-line cap.
- **D42 Rules from other layers without `section:`** are not an error: `validate` warns (naming the file and the skill's sections) and the rule lands in an engine-generated "Other" section listed last.
- **D43 D27(4) includes Starlette** (it ships anyio); the three templates change together, pytest-asyncio first when the repo has it.
- **D44 Worked example** (replaced by D48): its unmapped-domain-error test becomes a route-layer unit test with no database and no fake; its FastAPI entry point follows `fastapi-app-wiring` (`create_app(settings)` plus `asgi.py`).
- **D45 Post-pilot follow-ups:** split `pytest-async-tests` and `pytest-skip-xfail` out of `pytest` and add both to generate-tests and characterize; add `arch-composition-root` to review-architecture; move PT006/PT007 to `pytest-parametrize` and PT011/PT018 to `pytest-assertions`; D9's prompt merges.
- **D46 Confirmed mapping and engine choices:** (1) test pins: `monkeypatch` narrows to `monkeypatch.setenv` owned by `pytest-monkeypatch`, `from conftest import` moves to `pytest-conftest`, `composition over inheritance` to `design-composition-over-inheritance`, other pinned phrases move with their split rules; (2) `pydantic-typed-settings` gates on `has_dependency: pydantic-settings`; (3) `fastapi-*` rules gate on FastAPI only, `web-*`, security and DB rules on any web framework, DB rules also on SQLAlchemy or Alembic; (4) the five performance rules and early return sit in MEDIUM sections, `design-plugin-loading` stays MEDIUM; (5) small engine-written additions stay, marked "not vendored" in ATTRIBUTIONS, and there is no separate pre-commit rule; (6) 171 rules; (7) Covers clause lowercases titles except words like FastAPI and HTTP, two-column index tables, agent_harness `SKILL.md` gets the index; (8) no `[IMPACT]` tag in prompt or eval appendices, priority bands only for skills with sections; (9) in Continue's output, links to a skill's `references/` render as plain file names.

Round 6 (navigation and examples):

- **D47 Generated navigation in every `SKILL.md`.** After the hand-written intro and Quick Reference, the engine renders three parts: (1) a fixed "How to use this skill" paragraph (the index lists only the rules that apply to this repo, most important first; find the sections whose "open when" line matches the change, read those rules in full before editing, usually 1-3; open a reference or example when a rule names it or its open-when line matches, D58); (2) "Rules": one heading per active section (`### Mocking [CRITICAL]`), its one-line `open_when`, then a two-column table of its active rules; (3) "References and examples": generated from `playbook.references` entries (path, `open_when`, optional `applies_if`) whose gate passes. Every section declares `open_when`; every file under `references/` and `examples/` (license files excepted) is listed; a rule names a reference or example by path in a `see` list and in its Notes, as plain text. Hand-written "Picking references" bullets go away. Navigation chain: always-loaded context (Where map, skill nudges, descriptions whose Covers clause names sections) -> skill -> 1-3 rules -> reference or example.
- **D48 One canonical example app.** pca's `fastapi-hotel-api` is vendored and adapted to every engine decision as `web-application/examples/fastapi-hotel-api/` (about 20 files): session per request through a dependency, transaction boundary in the use case, not-found -> 404 and duplicate -> 409 at the error boundary, typed records between layers, SQLAlchemy 2.0 `Mapped` models, `create_app(settings)` plus `asgi.py`, injected clock and ids, unit tests on fakes and endpoint tests on the real engine in a rolled-back transaction, no course citations. Its `README.md` is the walkthrough and maps each file to the rules it demonstrates. It has its own `pyproject.toml`; a dedicated CI job runs its tests in an isolated environment, so the engine gains no dependency. `examples/` becomes a synced skill directory, and the entry's `applies_if` (`has_framework: fastapi`) suppresses both its listing and its files elsewhere. Rules of other skills point to example files only inside a `has_framework("fastapi")` Jinja branch. python_design's `worked-example.md` is dropped and its narrative moves into the README (replaces D44; amends D25, which excluded the app).
- **D49 Internal navigation references.** Each skill may add up to 3 engine-written references (`kind: internal`): decision guides that route a situation to the right rules across sections (for example which test double, which idiom per Python version, which check failure maps to which rule, the same operation across numpy, pandas, polars and torch). Each is at most 120 lines, names rule ids in plain text, never repeats a rule body, and is marked "not vendored" in ATTRIBUTIONS.

Round 10 (layout adapter):

- **D71 The document layout is configurable through a layout adapter** (amends D60's "fixed names" and ADR 0006). A `[layout]` table in the committed config sets `glossary`, `context_map`, `adr`, `architecture`, `specs`, `plans`, `research`, `agents` and `scratch`; a key left out keeps its D60 default, so a repo that sets nothing gets exactly D60. Every framework writes its paths in the D60 default form; when a repo's layout differs, `sync` rewrites exactly those default path prefixes in the synced files of core, bundled plugins and overlays, and `validate` reports every rewrite per file. A framework whose text uses other paths declares `layout_aliases` in its framework metadata file (D57), for example `"docs/superpowers/plans/" = "plans"`, and the adapter maps them too, under the default layout as well (only a repo with no [layout] and no aliases gets byte-identical output), so any spec-driven framework plugs into the same config without editing its text. The D61 always rule renders the configured paths through Jinja, and the D61 guard hook blocks writes outside the configured directories. File name patterns (`YYYY-MM-DD-<slug>.md`, `NNNN-slug.md`) stay fixed. This engine repo can set `specs = "specs"` and follow the frameworks without moving its files, which makes D62's migration optional.
- **D72 Code legibility for agents** (round 10; ideas distilled from Akita, "Clean Code para Agentes de IA", 2026-04-20, as reformulated by the owner, credited by name only): (1) new `python-meaningful-names` in `python-coding`, whose HIGH section becomes "Names, types and docstrings": distinctive, searchable names, the grep test (if a search for the name returns mostly unrelated code, the name is wrong), generic words only when qualified, one concept one name; `design-name-for-intent` keeps only the review angle (alike things named alike). (2) `design-dry-yagni-kiss` states why duplication is worse with an agent: it updates one copy and misses the others, so one home per piece of logic is refactor safety, not aesthetics. (3) new `arch-predictable-project-tree` in `python-architecture`: one path predicts the next, framework conventions are kept, no ad-hoc top-level folders or flat dumps. (4) new `pytest-first-properties` in `python-testing`: Fast, Independent, Repeatable, Self-validating, Timely, each pointing to the rule that owns the detail, plus one documented headless command with parseable output. Explicit types were already covered (always rule, `python-typing`, typed records).
- **D73 Code legibility, always-loaded** (round 10; same distilled source as D72, credited by name only). These are general clean-code principles for every reader, people and agents alike; the agent-specific cost is one supporting reason in each rule, never the only one. (1) New or strengthened rules: `python-small-units` (functions of about 4-20 lines, files under about 500, ideally 200-300) and `python-early-return`, retitled around shallow nesting (about two levels, one level of abstraction per function), both in a new HIGH `python-coding` section "Code shape" (early return moves up from MEDIUM, amending D46(4)); `python-error-messages-with-context` in the CRITICAL error section (the offending value via repr, the expected shape, the field); `design-single-responsibility` gains the rationale. (2) A new language-neutral always rule, "Code legibility" (`code-legibility`), right after project context: one line each for small units, one responsibility per module, shallow nesting, errors with context, searchable names, one home per piece of logic, a predictable tree and F.I.R.S.T unit tests, each ending with the skill and rule that hold the detail (all eight targets are ungated, so the names never dangle). Like every always rule it is written into each harness's always-loaded files: the root `AGENTS.md` (OpenCode, Codex and other AGENTS.md readers), Claude Code's `.claude/CLAUDE.md` and `.claude/rules/coding-agent-playbook.md`, and Continue's `.continue/rules/` file; its pointers are harness-neutral "skill -> rule" names, so the same text works whether the harness loads the skill by name or, like Continue, receives each rule as its own file. The Python house style drops its layout-axis line (moved here) and keeps "type-hint every signature". (3) The always-sections word cap rises from 240 to 450 to fit this rule and D61's layout rule; the 800 and 1,500 totals stay, and lane 0 measures them (amends D35 for this cap).

Round 11 (capabilities, asking for missing input, prompt sets):

- **D74 Framework capabilities.** `framework.toml` (D57, D71) gains a `[capabilities]` table mapping standard roles to the framework's own skill names: `clarify`, `clarify_with_docs`, `spec`, `plan`, `tdd`, `debug`, `review`, `verify` (mattpocock_skills: `clarify = "grill-me"`, `clarify_with_docs = "grill-with-docs"`, `spec = "to-spec"`, `plan = "to-tickets"`, `tdd = "tdd"`, `debug = "diagnosing-bugs"`, `review = "two-axis-review"`; superpowers: `clarify = "brainstorming"`, `plan = "writing-plans"`, `tdd = "test-driven-development"`, `debug = "systematic-debugging"`, `review = "requesting-code-review"`, `verify = "verification-before-completion"`). Templates get `framework_skill(role)` (the enabled framework's skill name, or nothing) and `skill_active(name)` (whether a core skill renders in this repo). Core text never names a plugin skill directly; a new framework plugs in by declaring its capabilities.
- **D75 Asking for missing information.** `playbook-creator` opens with a rule listing what each artifact needs before it is written (kind and layer, skill and section, gate and impact, source and its license) and asks for anything missing through `framework_skill("clarify")` (for example `grill-me` with mattpocock_skills), or directly when no framework is enabled. The always rule `project-context` renders the same pointer in its "ask before writing code when the scope or the approach is unclear" line.
- **D76 Prompt sets.** `catalog/core/prompts/v2/` holds a second version of each of the 9 core prompts, under the same names, chosen by a committed config key `prompts = "v2"`; the default stays `v1` during the pilot, so graded prompts and their evals stay frozen (D16), and the listing does not grow. Each v2 prompt adds: "Before you start" (the core skills to load for that task, filtered with `skill_active`), "If something is unclear" (the clarify capability, or ask the user) and "Check and improve your work" (the framework's `tdd`, `review`, `verify` or `debug` skill by role, and the core decision guides that apply). v2 keeps v1's `includes_rules`, so the opt-in eval comparison (D37) measures only the added skill guidance.
