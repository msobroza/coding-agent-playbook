# coding-agent-playbook
Multi-harness playbook engine

## Why coding-agent-playbook?

- **One source, every assistant.** Author your rules, prompts, and skills once
  as markdown + YAML frontmatter. The engine renders them into whatever each
  tool expects — `.continue/`, `.claude/`, `.opencode/`, and the universal
  `AGENTS.md` — so you stop hand-maintaining the same guidance in four formats.
- **Drift can't sneak in.** Generated files carry an `AUTOGENERATED` header and
  are verified by a `playbook sync --check` pre-commit hook: if the output no
  longer matches the canonical source, the commit fails. The context your
  assistants read is always in sync with the source of truth.
- **Context-aware, not noise.** A detector inspects the repo (dependencies,
  frameworks, ML stack, project kind) and each artifact's `applies_if` predicate
  decides what ships — a FastAPI rule only reaches FastAPI repos, the ML
  serialization-security rule only ML repos. Assistants get the rules that
  actually apply.
- **Built for organizations.** Three layers compose by artifact `id`: engine
  generic content → pip-installable org overlay packages → repo-local
  `playbook/` overrides. Central teams distribute standards as versioned
  dependencies; individual repos extend or override locally — no forking, no
  copy-paste.
- **Enterprise-friendly.** Copies, not symlinks (cross-platform,
  banking-safe). No telemetry, ever. No outbound network by default — even the
  pre-commit hooks run locally, so it works fully offline. Distribute via
  internal PyPI / git.
- **Mistakes caught before they ship.** `playbook validate` cross-checks the
  canonical source (prompt↔rule inclusion symmetry, eval-task back-references,
  typo'd predicate keys), and a lockfile records the engine version that
  produced each artifact, so regenerations are reproducible and reviewable in a
  diff.
- **Quality is measurable.** Prompts can declare paired eval tasks (positive +
  false-positive guards), so prompt behavior is testable rather than vibes —
  authored as `[gate]` / `[rubric]` layers and run end-to-end with
  `playbook eval --run`.

## Status

Engine and CLI are implemented: detector, renderer, five adapters
(Continue, Claude Code, OpenCode, AGENTS.md, and the opt-in
[Agent Harness](https://agentharnesses.io/specification)), the `playbook`
commands (`init` / `sync` / `check` / `validate` / `render` / `eval` /
`metrics` / `import-harness` / `validate-harness`), the Tier 0 eval schema
plus the v1.1 eval runner (`playbook eval --run`, deterministic layers live;
judged rubric scoring live via `--judge`), and the code-quality metrics gate. See
`SPEC.md` for the full design.

Working on the engine itself:

```bash
uv sync --extra dev   # install engine + dev tools
uv run pytest         # run the test suite
uv run playbook --version  # smoke-test the CLI
```

## Using the playbook in an external repo

Add the playbook to any repo that should get generated assistant context
(`.continue/`, `.claude/`, `.opencode/`, `AGENTS.md`) from the canonical rules
and prompts.

### 1. Install

Install the engine as a dev dependency, plus any organization overlay packages
that ship your team's rules and prompts:

```bash
uv add --dev coding-agent-playbook            # the engine (generic content)
uv add --dev playbook-rules-<org>             # optional: your org's overlay
```

`pip` works too: `pip install coding-agent-playbook`.

### 2. Initialize

```bash
playbook init
```

`playbook init` detects your stack, then writes:

- `.coding-agent-playbook.toml` — the committed project config (below);
- `.coding-agent-playbook.local.toml` — personal per-engineer overrides
  (gitignored automatically);
- a merged `.pre-commit-config.yaml` and installs the hooks;
- and runs `playbook sync` once to generate the initial artifacts.

### 3. Generate

```bash
playbook sync     # regenerate .continue/, .claude/, .opencode/, AGENTS.md
```

`playbook sync` is the workhorse — re-run it (or let the pre-commit hook run it)
whenever the canonical source or your dependencies change. `AGENTS.md` is always
generated regardless of which adapters are enabled.

### 4. Define which resources apply

Three layers compose, later overriding earlier **by artifact `id`** (SPEC §11):

1. **Engine generic content** — ships with `coding-agent-playbook`.
2. **Overlay packages** — installed org packages, enabled (and ordered) in config.
   They're auto-discovered through Python entry points; you just list them:

   ```toml
   # .coding-agent-playbook.toml
   schema_version = 1

   [project]
   name = "risk-models"
   kind = "python-application"          # python-library | ml-research | notebook
   description = "Counterparty risk scoring service"

   [overlays]
   enabled = ["playbook_rules_bnp"]     # ordered; later wins on id collision

   [adapters]
   enabled = ["continue", "claude_code", "opencode"]   # AGENTS.md always emitted
   # add "agent_harness" to also emit an Agent Harness tree (opt-in)
   ```

3. **Repo-local `playbook/`** — drop in per-repo rules, prompts, or eval tasks;
   anything here wins on `id` collision:

   ```text
   playbook/
   ├── rules/         # add a new rule, or override one by reusing its id
   ├── prompts/
   └── eval_tasks/
   ```

Not every resource renders everywhere: the detector inspects the repo and each
artifact's `applies_if` predicate gates it (a FastAPI rule won't ship to a
non-FastAPI repo; the ML serialization-security rule ships only to repos with an
ML stack). Run `playbook check` to see the detected facts and exactly which
rules/prompts are active — the fastest way to debug *"why isn't my rule
appearing?"*

## Agent Harness support (opt-in)

Beyond the four always-available targets, the playbook can render to and read from
the [Agent Harness](https://agentharnesses.io/specification) format — a
`HARNESS.md`-rooted tree of skills, prompts, rules, and references.

### The `agent_harness` adapter

Enable it by adding `agent_harness` to `[adapters] enabled`. It is **opt-in** —
not part of the default adapter set — and otherwise behaves like any other
adapter under `playbook sync`:

```toml
# .coding-agent-playbook.toml
[adapters]
enabled = ["continue", "claude_code", "agent_harness"]
```

`playbook sync` then emits a `HARNESS.md` plus `skills/`, `prompts/`, `rules/`,
and `references/` directories, alongside a `.playbook/manifest.toml` sidecar that
records everything the harness format can't represent — so the tree round-trips
back to canonical artifacts losslessly.

### Importing and validating harness trees

Two commands handle the reverse direction and structural linting:

```bash
playbook import-harness <path> [--into <dir>]   # harness tree → canonical artifacts (default ./playbook/)
playbook validate-harness <path> [--strict]     # structural checks (harnesses-ref-equivalent)
```

`import-harness` is lossless when the source carries a `.playbook/manifest.toml`
sidecar (a playbook-emitted harness) and best-effort otherwise (a foreign
harness), reporting every lossy assumption it makes. `validate-harness` checks
that `HARNESS.md` and every skill leaf carry a `name`/`description`, and warns
(or, with `--strict`, fails) on missing routing files or undescribed content
files.

## Pre-commit integration

`coding-agent-playbook` ships a `.pre-commit-hooks.yaml` so consumer repos can wire `playbook sync --check` into their pre-commit pipeline directly:

```yaml
# In your repo's .pre-commit-config.yaml:
- repo: https://github.com/msobroza/coding-agent-playbook
  rev: v0.1.0a0     # pin to a released tag
  hooks:
    - id: playbook-sync-check
```

After `pre-commit install`, every commit verifies that the generated `.continue/`, `.claude/`, `.opencode/`, and `AGENTS.md` files match what the engine would produce. Drift fails the commit with a pointer to run `playbook sync` to regenerate.

`playbook init` writes a starter `.pre-commit-config.yaml` for you — an **air-gapped-friendly** config whose hooks are all `repo: local` + `language: system` (the sync check plus `ruff`/`ruff-format`/`mypy`), so pre-commit never clones a remote hook repo. The flip side: those tools must already be installed in your environment, since `language: system` runs them from PATH rather than installing them. See SPEC.md §13.2 for the full template and the hooks deliberately left out.

### Hooks

| Hook ID | When it runs | What it does |
| --- | --- | --- |
| `playbook-sync-check` | Every commit | Runs `playbook sync --check`; fails the commit on drift. Consumer-facing. |
| `playbook-validate` | Manual only (`pre-commit run --hook-stage manual playbook-validate`) | Runs `playbook validate`; surfaces canonical-source mistakes (typo'd `applies_if` keys, orphan eval tasks, etc.). Overlay-author-facing. |
| `playbook-metrics` | Every commit (Python files) | Runs `playbook metrics --baseline git:HEAD`; fails the commit when staged Python worsens vs `HEAD`. **Static only** — never runs your test suite. |

## Code-quality metrics gate

`playbook metrics` is a standalone, **opt-in** code-quality gate. It measures Python with deterministic static metrics — cyclomatic complexity, weighted methods per class (WMC), LCOM4, depth of inheritance, an approximate coupling-between-objects, and (with the optional extra) the maintainability index — and grades the result either against absolute thresholds or, by default, as a **non-regression** check against a baseline. It is independent of `playbook sync`: nothing about your generated assistant context depends on it.

```bash
playbook metrics                              # measure src/ against absolute thresholds
playbook metrics --baseline git:HEAD          # fail if the working tree worsens vs HEAD
playbook metrics src tests --format json      # machine-readable findings
playbook metrics --strict                     # promote warnings to failures (non-zero exit)
```

It exits `0` on pass, `1` on a breach, and `2` on a usage error (bad path, bad baseline, malformed `[metrics]` config). Defaults and per-metric thresholds live in a `[metrics]` table in `.coding-agent-playbook.toml`. Under the hood each metric is wrapped in a **check** (a threshold or non-regression grader) and the checks are folded into one **rubric** report — the `Metric` / `Check` / `Rubric` model (see SPEC §21).

### Running tests and coverage (`--run-tests`)

`--run-tests` additionally runs the **execution** metrics — `test_pass_rate` and `coverage` — which shell out to your project's own `pytest` (and `pytest-cov`) and parse the standard junit/coverage XML. These have side effects and cost, so they are **opt-in and never part of the default pre-commit hook**; run them in CI or on demand:

```bash
playbook metrics --run-tests                          # also run the suite + measure coverage
playbook metrics --run-tests --baseline git:HEAD      # fail on new test failures / coverage drop
playbook metrics --run-tests --test-cmd "pytest -q"   # override the test command
```

The engine adds no dependency for this — your target project supplies `pytest`/`pytest-cov`.

### The `metrics` optional extra (maintainability index)

The core gate is **stdlib-only** and runs with nothing extra installed. The maintainability index is the one metric backed by [`radon`](https://radon.readthedocs.io/), so it ships as an optional extra; without it that single metric is transparently skipped:

```bash
pip install 'coding-agent-playbook[metrics]'   # adds radon for maintainability_index
```

## Running evals

`playbook eval` enumerates the prompt-to-task graph (`--list` / `--show`); with `--run` (v1.1) it **executes** a single task end-to-end against an agent and grades it:

```bash
playbook eval refactor-extract-helper --run --runner claude_code   # real: drive the Claude Code CLI
playbook eval refactor-extract-helper --run --runner opencode       # real: drive the OpenCode CLI
playbook eval refactor-extract-helper --run --runner fake          # hermetic demo / CI: no network, no CLI
playbook eval refactor-extract-helper --run --judge llm --samples 3 # also score [rubric] via an LLM judge
playbook eval refactor-extract-helper --run --full-scoring          # run every check (no short-circuit)
playbook eval refactor-extract-helper --run --format json          # machine-readable report
```

A task declares its success criteria as **layers** (SPEC §6.5.3): a deterministic `[gate]` (file + metric checks composed by a tiny boolean `expr`), an optional llm-judge `[rubric]` (weighted criteria), a `[verdict]` (a boolean expression over the two layers), and an optional cross-trial `[aggregate]` (`pass@k` / `pass^k`). They compile into one **rubric** of checks (the `Metric` / `Check` / `Rubric` model, SPEC §21): the `[gate]` layer — file predicates (`file_exists` / `file_contains` / `file_unchanged` / `file_forbidden`) and static/execution metric checks (0–1 normalized thresholds, non-regression vs the `setup/` baseline) — is scored **deterministically** into one report, rendered like `playbook metrics`, and the per-trial verdict is **derived** from the layer results. Two opt-in real runners ship — `claude_code` (the default, drives the `claude` CLI) and `opencode` (drives the `opencode` CLI) — both `available()`-gated on their binary and never exercised in CI; `--runner fake` is the hermetic driver for demos and CI. There is no `--run-tests` flag — a task runs the suite iff its `[gate]` references an execution metric (`coverage` / `test_pass_rate`). Exit `0` on a passing report, `1` on a failing one, `2` on a usage error (unknown task/runner, or a real runner whose CLI is not on `PATH`). Judged `[rubric]` scoring (v1.1 R2) is **opt-in via `--judge`**: pick a judge from the `coding_agent_playbook.judges` group (the shipped `llm` shells out to the `claude` CLI, `available()`-gated), and `--samples N` averages N gradings per criterion. Omit `--judge` for a deterministic-only run (the rubric layer skips; a skipped layer is neutral in the verdict). A cost-tiered scheduler runs the cheap deterministic checks first and **short-circuits once the gate is lost** — so a failing file/metric check never spends an LLM call; `--full-scoring` forces every check to run for a complete report.

A handle can also `{ref = "name"}` a **named gate or rubric** instead of inlining: in the `[gate]` layer it resolves a composed boolean gate registered via `@register_gate` (the `coding_agent_playbook.gates` group), in the `[rubric]` layer a code-defined `Rubric` subclass registered via `@register_rubric` (the `coding_agent_playbook.rubrics` group) — so several tasks share one gate/rubric by name. The engine ships no builtin gates or rubrics; both are third-party extension points.
